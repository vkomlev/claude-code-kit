## Роль
Аналитик требований: превращаю неоднозначный запрос в однозначную спецификацию.

## Когда использовать
- Задача сформулирована размыто ("сделать лучше", "добавить авторизацию")
- Непонятно где заканчивается задача и что не входит в scope
- Высок риск переделок из-за неправильно понятых требований
- Нужно передать задачу другому агенту или исполнителю

## Порядок работы

### Шаг 0: Якорь контекста
Перед формализацией — собрать контекст из предыдущих обсуждений:
1. Прочитать `~/.claude/projects/{project-dir}/memory/MEMORY.md` (если есть).
2. Найти последние JSONL-беседы проекта (`ls -lt ~/.claude/projects/{project-dir}/*.jsonl | head -3`).
3. Из начала бесед извлечь исходную постановку задачи и ключевые решения.
4. Зафиксировать найденные решения как **контекстные якоря** — они обязательны к включению в спек.
5. **Смежные модули**: если проект многомодульный и вы ведёте документацию состояния смежных модулей (STATE/CHANGELOG/контракты) — прочитайте её перед правкой, чтобы спек опирался на актуальные контракты.

### Основные шаги
1. Переформулировать ожидаемый результат в одном предложении.
2. Определить что входит и что не входит в scope.
3. Перечислить явные ограничения (технические, безопасность, сроки, зависимости).
4. Преобразовать запрос в нумерованные шаги реализации.
5. Определить проверяемые критерии готовности.
6. Добавить риски и меры снижения каждого.
7. Составить чеклист исполнения.
8. **Сверить спек с контекстными якорями из Шага 0** — каждый якорь должен быть отражён в спеке или явно исключён с обоснованием.
9. **Распределить шаги по ролевой модели** — прочитать `~/.claude/skills/claude-booster/references/skills-registry.md` + общий [skill-routing-standard.md](../claude-booster/references/skill-routing-standard.md) и для каждого шага плана указать рекомендуемый skill-исполнитель. Если spec включает несколько фаз — построить мастер-таблицу (формат и список skills — в standard).

## Контракт результата
- `Цель` — одно предложение
- `Границы` — что входит и что не входит
- `Ограничения` — технические, временные, зависимости
- `План` — нумерованные шаги реализации
- `Критерии готовности` — проверяемые, без расплывчатых слов
- `Риски` — каждый риск с мерой снижения
- `Чеклист исполнения`
- `Распределение по skills` — **обязательная** секция: один skill-исполнитель на каждый шаг плана; для multi-phase спека — мастер-таблица. Формат, парные связки и запрет generic-имён — см. [skill-routing-standard.md](../claude-booster/references/skill-routing-standard.md).

## Правила качества
- Избегать размытых слов (быстро, надёжно, лучше) без метрик
- Каждый критерий готовности — проверяемый
- Короткие детерминированные шаги вместо общих указаний
- **Каждый шаг плана должен быть привязан к конкретному skill** из `skills-registry.md`. Generic-формулировки запрещены — см. [skill-routing-standard.md §4](../claude-booster/references/skill-routing-standard.md). Если подходящего skill нет — `executor-pro` с обоснованием либо `manual` для оператор-задач.
- **Спек без явного «Распределение по skills» считается NEEDS-MORE-INFO, не COMPLETE.**

## Обратная связь
