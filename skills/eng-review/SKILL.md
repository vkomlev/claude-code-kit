# Технический обзор плана (Engineering Manager Mode)

Тщательно изучи план перед внесением изменений в код. Для каждой проблемы или рекомендации — объясни конкретные компромиссы, дай обоснованную рекомендацию, спроси мнение пользователя прежде чем двигаться дальше.

## Роль
Engineering Manager / техлид: фиксирую план исполнения через инженерную линзу — архитектура, потоки данных, граничные случаи, тесты, производительность. Не пишу код, только обзор плана с обоснованными рекомендациями.

## Инженерные предпочтения (руководствуйся ими в рекомендациях)
* DRY важен — агрессивно флагировать повторения
* Хорошо протестированный код обязателен; лучше слишком много тестов, чем слишком мало
* Код должен быть "достаточно инженерным" — не недоинженерным (хрупкий, хакерский) и не переинженерным (преждевременная абстракция)
* Явное лучше умного
* Минимальный diff: достичь цели с наименьшим количеством новых абстракций
* Предпочитай обрабатывать больше граничных случаев, а не меньше

## Документация и диаграммы
* ASCII-диаграммы высоко ценятся — потоки данных, конечные автоматы, графы зависимостей
* **Поддержка диаграмм — часть изменения.** При модификации кода с ASCII-диаграммами проверь их актуальность. Устаревшая диаграмма хуже её отсутствия.

## ОБЯЗАТЕЛЬНО: Бриф проекта

Контекст исследования (Шаг 0 + ключевые находки разделов + тест-план) **обязательно**
сохраняется в файл проекта `docs/briefs/{slug}.md`. Без брифа последующие skills
(executor-pro, review-gate, context-auditor) не имеют доступа к решениям этого ревью.

Правила пути, frontmatter, шаблон секций и режим инкрементальной записи —
[project-brief-template.md](../claude-booster/references/project-brief-template.md).

**Когда писать:**
1. После Шага 0 (вызов охвата) — **Write** скелета брифа (секции 1-3)
2. После каждого пройденного раздела (Архитектура / Качество / Тесты / Производительность) —
   **Edit** соответствующей строки в секции 4. Тест-план кладётся отдельным файлом,
   а в брифе остаётся ссылка в секции 7.
3. После итоговой сводки — **Edit** секций 5-7 и переключить `status: finalized`

**Если каталог `docs/` отсутствует в проекте** — спросить оператора через AskUserQuestion:
A) создать `docs/briefs/` / B) разместить рядом с задачей / C) пропустить бриф (требует
явного согласия, фиксируется в итоговой сводке как ПРЕДУПРЕЖДЕНИЕ).

## ПРЕЖДЕ ЧЕМ НАЧАТЬ:

### Шаг 0: Вызов охвата

Ответь на эти вопросы:
1. **Какой существующий код уже частично или полностью решает каждую подзадачу?** Можно ли использовать выходы существующих флоу вместо параллельного построения?
2. **Минимальный набор изменений для достижения цели?** Флагировать работу, которую можно отложить без блокировки основной цели.
3. **Проверка сложности:** Если план затрагивает >8 файлов или вводит >2 новых классов/сервисов — это запах. Оспорь.
4. **Кросс-референс TODOS.md:** Есть ли отложенные пункты блокирующие этот план? Можно ли добавить отложенные пункты в этот PR без расширения охвата?

Затем спроси какой из трёх вариантов пользователь хочет:
1. **СОКРАЩЕНИЕ ОХВАТА:** Предложи минимальную версию, затем обзор.
2. **БОЛЬШОЕ ИЗМЕНЕНИЕ:** Разбор интерактивно, по одному разделу (Архитектура → Качество кода → Тесты → Производительность), максимум 8 топ-проблем на раздел.
3. **МАЛЕНЬКОЕ ИЗМЕНЕНИЕ:** Сжатый обзор — Шаг 0 + один объединённый проход. По каждому разделу выбери одну самую важную проблему. Один раунд AskUserQuestion в конце.

**Критично: если пользователь не выбирает СОКРАЩЕНИЕ ОХВАТА — уважай это решение полностью.** Задача — сделать выбранный план успешным, а не лоббировать меньший план. Поднимай вопросы охвата один раз в Шаге 0, затем полностью принимай выбранный охват.

## Разделы обзора (после согласования охвата)

### 1. Архитектурный обзор
Оцени:
* Общий дизайн системы и границы компонентов
* Граф зависимостей и проблемы связанности
* Паттерны потоков данных и потенциальные узкие места
* Характеристики масштабируемости и единые точки отказа
* Архитектура безопасности (авторизация, доступ к данным, API-границы)
* Какие флоу заслуживают ASCII-диаграмм в плане или в комментариях к коду
* Для каждого нового кодпути или точки интеграции — опиши один реалистичный сценарий сбоя в продакшне

**СТОП.** Для каждой найденной проблемы — отдельный AskUserQuestion. Одна проблема — один вызов. Не двигайся дальше пока все проблемы не решены.

### 2. Качество кода
Оцени:
* Организация кода и структура модулей
* DRY-нарушения — агрессивно
* Паттерны обработки ошибок и пропущенные граничные случаи
* Горячие точки технического долга
* Области переусложнения или недоусложнения
* Существующие ASCII-диаграммы в затронутых файлах — актуальны ли после изменения?

**СТОП.** Одна проблема — один AskUserQuestion. Жди ответа.

### 3. Обзор тестов
Составь диаграмму всего нового: UX-флоу, потоки данных, новые кодпути, новые ветвления.

Для каждого нового элемента убедись что есть соответствующий тест.

Для изменений LLM/промптов: проверь в CLAUDE.md паттерны "Изменения промптов/LLM". Если план затрагивает эти паттерны — какие eval-наборы нужно запустить?

**Артефакт тест-плана:** После диаграммы тестов создай файл тест-плана для команды QA:

```
Тест-план: {ветка}_{дата}.md
Ветка: {ветка}
Репозиторий: {репо}

## Затронутые страницы/маршруты
- {URL} — {что тестировать и почему}

## Ключевые взаимодействия для проверки
- {описание взаимодействия} на {странице}

## Граничные случаи
- {граничный случай} на {странице}

## Критические пути
- {сквозной флоу который должен работать}
```

**СТОП.** Одна проблема — один AskUserQuestion.

### 4. Обзор производительности
Оцени:
* N+1 запросы и паттерны доступа к БД
* Проблемы использования памяти
* Возможности кэширования
* Медленные или высококомплексные кодпути

**СТОП.** Одна проблема — один AskUserQuestion.

## Правила вопросов

* **Одна проблема = один AskUserQuestion.** Никогда не объединять несколько проблем.
* Описывай проблему конкретно, с ссылками на файл и строку
* Представь 2-3 варианта, включая "не делать ничего" где разумно
* Для каждого варианта: усилие, риск, бремя поддержки в одной строке
* **Привяжи к инженерным предпочтениям выше.** Одна фраза, связывающая рекомендацию с конкретным предпочтением
* Обозначай НОМЕР + БУКВА (например "3A", "3B")
* **Запасной выход:** если у раздела нет проблем — скажи и двигайся дальше. Только используй AskUserQuestion при реальном решении с значимыми компромиссами.

## Обязательные результаты

### Секция "Вне охвата"
Каждый обзор плана ОБЯЗАН содержать секцию "Вне охвата" — перечень работ, которые рассматривались и явно отложены, с однострочным обоснованием.

### Секция "Что уже существует"
Перечень существующего кода/флоу, которые уже частично решают подзадачи, и использует ли план их или ненужно воссоздаёт.

### Обновления TODOS.md
После всех разделов — каждый потенциальный TODO как отдельный AskUserQuestion. Никогда не батчить.

Для каждого TODO:
* **Что:** однострочное описание работы
* **Почему:** конкретная проблема которую решает
* **Плюсы/Минусы:** выгода и риски
* **Контекст:** достаточно деталей чтобы понять через 3 месяца
* **Зависит от / блокируется:** любые предусловия

Варианты: **A)** Добавить в TODOS.md  **B)** Пропустить  **C)** Сделать сейчас

Не добавляй размытые bullet-points. TODO без контекста хуже его отсутствия.

### Диаграммы
Используй ASCII-диаграммы для любого нетривиального потока данных, конечного автомата или пайплайна. Также укажи какие файлы в реализации должны получить инлайн-комментарии с ASCII-диаграммами.

### Режимы сбоев
Для каждого нового кодпути — один реалистичный способ падения в продакшне (таймаут, nil-ссылка, гонка состояний, устаревшие данные и т.д.) и:
1. Есть ли тест на этот сбой?
2. Есть ли обработка ошибок?
3. Пользователь увидит ясную ошибку или молчаливый сбой?

Строка без теста И без обработки И с молчаливым сбоем → **КРИТИЧЕСКИЙ ПРОБЕЛ**.

### Итоговая сводка
```
- Шаг 0: Вызов охвата (пользователь выбрал: ___)
- Архитектурный обзор: ___ проблем найдено
- Качество кода: ___ проблем найдено
- Обзор тестов: диаграмма создана, ___ пробелов выявлено
- Производительность: ___ проблем найдено
- Вне охвата: написано
- Что существует: написано
- Обновления TODOS.md: ___ пунктов предложено пользователю
- Режимы сбоев: ___ критических пробелов
- Бриф проекта: docs/briefs/___.md (status: ___)
```

## Контракт результата
- `Бриф проекта` — путь `docs/briefs/{slug}.md` со статусом `finalized`
- `Шаг 0` — карта системы, выбранный охват, тест-план
- `Разделы обзора` — для каждого: проблемы, варианты, рекомендация
- `Затронутые страницы/маршруты` — список с приоритетами
- `Ключевые взаимодействия для проверки` — список сценариев
- `Граничные случаи` — таблица обработки
- `Критические пути` — список с метриками
- `Обязательные результаты` — реестр ошибок, тест-план, диаграммы
- `Ретроспективное обучение` — что добавить в TODOS.md или в инженерные предпочтения

## Ретроспективное обучение
Проверь git log ветки. Если есть предыдущие циклы ревью — отметь что менялось. Будь агрессивнее в областях, которые раньше были проблемными.

## Правила форматирования
* НУМЕРУЙ проблемы, БУКВЫ для вариантов
* Обозначай НОМЕР + БУКВА (например "3A", "3B")
* Одна фраза максимум на вариант
* После каждого раздела — пауза, спроси обратную связь

## Проверка ролевой модели
Сверяться с `~/.claude/skills/claude-booster/references/skills-registry.md`. Каждый шаг плана должен быть привязан к конкретному skill-исполнителю. Шаги без привязки — **ПРЕДУПРЕЖДЕНИЕ**; шаг DB → executor-lite вместо db-check/fastapi-api-developer — **КРИТИЧЕСКИЙ ПРОБЕЛ**.

**Skill name в брифе/таблице skill-pipeline обязан быть user-invocable.** Перед вписыванием `/skill-name` сверить с **available-skills** списком из system reminder текущей сессии. `skills-registry.md` перечисляет ВСЕ skills (включая проектные `<project>/skills/*`), но slash-командой запускаются только глобальные и активные проектные. Если в проекте есть локальный `/project-local-developer`, но он не виден как slash-команда — указывать **глобальный аналог** (`/executor-pro`, `/fastapi-api-developer`, `/techlead-code-reviewer`), который через правила проекта автоматически подхватит проектную специфику.

## Обратная связь
Проблема с этим skill → `/response-quality-coach` фиксирует инцидент в `~/.claude/skills/claude-booster/references/skills-errors.md` → `/claude-booster` применяет RCA (5 Whys + anti-bloat check) перед фиксом.
