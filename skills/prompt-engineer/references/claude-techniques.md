# Техники для Claude-specific режима

Источник: Anthropic official docs + наблюдения за поведением Claude 4.x.

## 1. XML-теги как структура (КРИТИЧНО)
Claude обучен особенно хорошо реагировать на XML-теги. Без них модель угадывает границы секций по интонации текста — теряется до 30% качества.

**Базовый набор тегов:**
```xml
<context>
  [Фактура: что за проект, ситуация, ограничения]
</context>

<task>
  [Одна фраза: что нужно сделать]
</task>

<instructions>
  [Развёрнутые шаги или правила]
</instructions>

<examples>
  <example>
    <input>...</input>
    <output>...</output>
  </example>
</examples>

<output_format>
  [Точный шаблон вывода]
</output_format>

<constraints>
  [Что нельзя]
</constraints>
```

Теги именовать осмысленно: `<customer_email>`, `<api_response>`, а не общие `<data>`.

## 2. System vs User разделение
- **System prompt:** роль, постоянный контекст, инструкции, формат вывода, ограничения, few-shot примеры
- **User message:** конкретный запрос к этой роли, переменные данные

Антипаттерн: смешивать роль и запрос в одном user-сообщении. Так теряется кэшируемость system prompt и стоимость растёт.

## 3. Prefill assistant response
Если нужен жёсткий формат — начать ответ за модель:
```python
messages=[
  {"role": "user", "content": "Извлеки данные из текста..."},
  {"role": "assistant", "content": "{"}   # prefill — модель продолжит JSON
]
```
Применять для: JSON, XML, конкретный markdown-заголовок, отказ от вступления («Конечно, вот ваш ответ…»).

## 4. Chain-of-thought (CoT)
Три уровня:
1. **Базовый:** добавить «Думай шаг за шагом» — простой буст
2. **Управляемый:** перечислить конкретные фазы мышления
3. **Структурированный:** обернуть в `<thinking>` теги, ответ — в `<answer>`

Структурированный — лучший: ответ извлекается программно, но рассуждения остаются в логах для отладки.

```xml
<instructions>
Перед ответом проанализируй задачу в <thinking>, затем дай решение в <answer>.
</instructions>
```

## 5. Extended thinking (Claude 4+)
Для сложных задач включить thinking-режим через API параметр. Не дублировать CoT-инструкции в промпте — модель уже думает. Промпт должен описывать задачу и формат вывода, не процесс мышления.

## 6. Few-shot 2-5 примеров
- Меньше 2 — модель не улавливает паттерн
- Больше 5 — переобучение на конкретику, теряется обобщение
- Покрывать: типичный кейс, граничный кейс, отказной кейс
- Оборачивать каждый в `<example>` с `<input>` и `<output>`

## 7. Role prompting
В первой строке system prompt — конкретная роль:
- Плохо: «Ты ассистент»
- Хорошо: «Ты опытный SRE с 10-летним стажем работы с Kubernetes в финтехе»

Роль значительно поднимает качество в доменных задачах. Не путать с «личностью» — роль это профессиональный контекст, не характер.

## 8. Prompt caching (для production)
- System prompt + tool definitions помечать `cache_control: ephemeral`
- Стабильная часть промпта (>1024 токенов для Sonnet, >2048 для Opus) кэшируется на 5 минут
- Кэш-хит снижает стоимость в 10 раз, латентность — в 2 раза
- Не менять system prompt между запросами без необходимости

## 9. Output контракт через формат
Не описывать формат словами — показывать буквальный шаблон:

Плохо:
```
Верни JSON со списком ошибок и их критичностью
```

Хорошо:
```xml
<output_format>
{
  "issues": [
    {
      "id": "string — уникальный идентификатор",
      "severity": "critical | warning | info",
      "line": "number",
      "message": "string"
    }
  ]
}
</output_format>
```

## 10. Negative instructions
Claude плохо обрабатывает чистые запреты. Переформулировать в позитив:
- Плохо: «Не используй жаргон»
- Хорошо: «Используй термины уровня senior engineer, объясняй аббревиатуры при первом упоминании»

## Чеклист Claude-promo
- [ ] XML-теги для секций
- [ ] System и user разделены
- [ ] Output format задан буквальным шаблоном
- [ ] Few-shot 2-5 примеров (если задача нетривиальная)
- [ ] Роль конкретна, не «ассистент»
- [ ] Запреты переформулированы в позитив
- [ ] Длинные стабильные части подходят для кэширования
- [ ] Prefill использован, если нужен жёсткий формат
