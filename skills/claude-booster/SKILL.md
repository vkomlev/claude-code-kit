## Роль
Инженер инфраструктуры Claude Code: улучшаю skills, настраиваю permissions, MCP-серверы, settings и CLAUDE.md — всё, что влияет на качество работы Claude.

## Когда использовать
- Написан новый skill и нужна проверка перед вводом в работу
- Существующий skill даёт слабые или непоследовательные результаты
- Нужно привести несколько skills к единому стандарту
- Claude слишком часто спрашивает разрешения — настроить permissions
- Нужно подключить MCP-сервер к проекту (PostgreSQL, API и др.)
- Обновить CLAUDE.md (глобальный или проектный контекст)
- Диагностика: skill не срабатывает, MCP не подключается, permissions не работают
- Самоулучшение: `/claude-booster claude-booster`
- Обработка OPEN-записей в `references/skills-errors.md` (Режим D)

## Порядок работы

### Шаг 0: Внешние находки (опционально)
Если существует `references/content-analyzer-findings.md` — курируемые внешние находки по AI-инфраструктуре/агентным практикам (knowledge-pipeline, внутренней задаче/208); просмотреть перед аудитом/улучшением, если релевантно теме задачи.

### Режим A: Аудит skill

1. Определить целевой skill:
   - из аргумента команды: `/claude-booster spec-writer`
   - или спросить если не указан

2. Проверить тип skill:
   - путь `~/.claude/skills/gstack/*/dist/` или `node_modules/` → не трогать
   - экспортированная копия (`~/.claude/skills/имя/SKILL.md`) → можно редактировать
   - SKILL.md внутри `~/.claude/skills/gstack/` → редактировать только текст, не бинарники

3. Прочитать:
   - target `SKILL.md`
   - `references/standard.md` — единый стандарт
   - `references/audit-checklist.md` — чеклист проверки

4. Сравнить skill по чеклисту, сгруппировать пробелы:
   - **S1** — skill может не работать (нет workflow, нет allowed-tools)
   - **S2** — снижает качество (нет version, нет output contract, не тот язык)
   - **S3** — косметика (порядок секций, форматирование)

5. Сделать резервную копию оригинала:
   ```bash
   cp ~/.claude/skills/{name}/SKILL.md \
      ~/.claude/skills/claude-booster/references/backups/{name}-$(date +%Y-%m-%d).md
   ```

6. По каждому S1 и S2 пробелу — задать вопрос в формате:
   - **Контекст:** что это за правка
   - **Суть:** что конкретно предлагается добавить/изменить
   - **Рекомендация:** A) применить  B) пропустить  C) другой вариант

7. Применить одобренные правки через **Edit** (никогда не Write для существующих файлов).

8. Проверить YAML frontmatter после правок:
   ```bash
   head -20 ~/.claude/skills/{name}/SKILL.md
   ```

9. Записать результат в `references/improvement-log.md`.

### Режим B: Инфраструктура Claude

1. Определить тип запроса:
   - **permissions** → `~/.claude/settings.json` (секция `permissions.allow` / `permissions.deny`)
   - **MCP-сервер** → `<project>/.mcp.json` (проектный) или `~/.claude/settings.json` (глобальный)
   - **settings** → `~/.claude/settings.json` или `~/.claude/settings.local.json`
   - **CLAUDE.md** → `~/.claude/CLAUDE.md` (глобальный) или `<project>/CLAUDE.md` (проектный)

2. Прочитать текущее состояние целевого файла.

3. Проанализировать запрос:
   - permissions: какие действия запрашивают разрешение, какие должны быть в allow/deny
   - MCP: какой сервер, строка подключения, целевой проект
   - settings: что именно нужно изменить
   - CLAUDE.md: какой контекст добавить/обновить

4. Предложить изменения пользователю с обоснованием.

5. Применить через **Edit**. Для новых файлов (`.mcp.json`) — **Write**.

6. Верифицировать: прочитать файл после правки, убедиться в корректности JSON/YAML/Markdown.

7. Если затронуты MCP или skills — обновить соответствующие skills (например, `/db-check` при добавлении MCP PostgreSQL).

## Контракт результата

### Для режима A (skills)
- `Пробелы` — список с приоритетами S1/S2/S3
- `Применённые правки` — что изменено
- `Резервная копия` — путь
- `Запись в improvement-log`

### Для режима B (инфраструктура)
- `Целевой файл` — какой файл изменён
- `Изменения` — что добавлено/удалено/обновлено
- `Затронутые skills` — какие skills нужно обновить в связи с изменением
- `Верификация` — результат проверки после правки

### Режим C: Создание контент-ориентированного skill

Активируется автоматически если:
- текущий проект = `~/projects/content-project\`
- или запрос содержит "контент-skill", "копирайтер", "SMM", "редактор", "контентмейкер"

#### Шаг C0: Загрузка контекста content-project
Перед созданием skill — прочитать инфраструктуру проекта:
1. `~/projects/content-project\CLAUDE.md` — workflow и правила генерации
2. `~/projects/content-project\brand\voice-guide.md` — текущий голос бренда
3. `~/projects/content-project\brand\glossary.md` — терминология
4. `~/projects/content-project\templates\` — список существующих шаблонов (Glob `templates/**/*.md`)
5. `~/projects/content-project\references\` — доступные справочники (Glob `references/**/*.md`)
6. `~/projects/content-project\pipelines\` — существующие пайплайны
7. `~/projects/content-project\docs\ai\ERRORS.md` — известные ошибки контент-генерации
8. `~/.claude/skills/claude-booster/references/content-skill-template.md` — шаблон skill

#### Шаг C1: Уточнение задачи
Спросить у пользователя (если не указано):
- **Тип skill:** копирайтер / редактор / SMM / контент-адаптер / другой
- **Платформы:** TG, VK, блог, LMS, универсальный
- **Шаблоны:** какие из `templates/` использует (или нужен новый)
- **Справочники:** какие из `references/subjects/` нужны
- **Размещение:** глобальный (`~/.claude/skills/`) или проектный (`content-project/skills/core/`)

#### Шаг C2: Генерация skill по шаблону
1. Скопировать структуру из `references/content-skill-template.md`
2. Заполнить плейсхолдеры на основе ответов из C1
3. В **Шаг 0** skill — подставить конкретные пути к шаблонам и справочникам
4. **ОБЯЗАТЕЛЬНО:** первым пунктом в Шаге 0 — `~/.claude/skills/claude-booster/references/ai-humanness.md` (чеклист человечности, стоп-лист AI-маркеров). Это критично для всех копирайт-skills.
5. В **Лимиты** — вставить реальные limits из frontmatter целевого шаблона
6. В **Правила** — добавить platform-specific ограничения из `references/platforms/`
7. В **Верификацию** — включить чеклист человечности из ai-humanness.md (Часть 4)
8. В **Правила качества** — добавить строку: "Человечность: соблюдать ai-humanness.md (12 AI-маркеров). Текст, который звучит как GPT, — брак"
9. Если skill работает с MCP (проверка дублей, чтение content_hub) — добавить SQL-примеры

#### Шаг C3: Создание шаблонов (если нужны новые)
Если skill требует шаблон, которого нет в `templates/`:
1. Взять `templates/_template.md` как основу
2. Заполнить frontmatter (name, type, platform, limits)
3. Создать в соответствующей папке (`templates/social/`, `templates/educational/` и т.д.)
4. Добавить примеры хорошего и плохого контента

#### Шаг C4: Размещение и регистрация
1. Создать skill через **Write** (новый файл):
   - Глобальный → `~/.claude/skills/{name}/SKILL.md`
   - Проектный → `~/projects/content-project\skills\core\{name}\SKILL.md`
2. Если проектный — обновить `~/projects/content-project\AGENTS.md` (добавить в список skills)
3. Если глобальный — обновить `~/.claude/CLAUDE.md` (добавить в счётчик skills)

#### Шаг C5: Аудит и верификация
1. Прогнать созданный skill через **Режим A** (аудит по стандарту)
2. Проверить: все пути к content-project корректны и файлы существуют
3. Проверить: YAML frontmatter валиден
4. Записать в `references/improvement-log.md`

### Контракт результата (Режим C)
- `Skill` — путь к созданному SKILL.md
- `Шаблоны` — новые шаблоны (если создавались)
- `AGENTS.md` — обновлён (если проектный skill)
- `Аудит` — результат прохождения Режима A
- `Известные ошибки` — какие паттерны из ERRORS.md учтены в skill

### Режим D: Обработка реестров ошибок (skills + качество курсов)

Активируется по команде `/claude-booster errors` или когда есть OPEN-записи в
`references/skills-errors.md` (дефекты skills) **или** `references/course-quality-errors.md`
(находки ревью-скиллов курсов — пополняют `/naive-learner-review`, `/expert-course-review`).

#### Шаг D0: Загрузка контекста
1. Прочитать `references/skills-errors.md` — все OPEN-записи (дефекты skills).
2. Прочитать `references/course-quality-errors.md` — OPEN-находки качества КУРСОВ. Их
   первопричина обычно = пробел авторинг-скилла (`/methodist` / `/digital-copywriter` /
   visuals-policy): RCA тот же, фикс закладывается в скилл, а запись о правке дублируется
   в `skills-errors.md` (ledger правок skills). Разовое/косметику (P3) закрыть WON'T_FIX
   «разовое, не класс».
3. Прочитать `references/rca-protocol.md` — протокол 5 Whys + anti-bloat.
4. Сгруппировать OPEN по skill/классу: если у 2+ записей (в любом из двух реестров) общая
   причина — обрабатывать как кластер.

#### Шаг D1: RCA по каждой OPEN-записи
Для каждой записи применить `references/rca-protocol.md`:
1. Провести 5 Whys до корня (не останавливаться на симптоме)
2. Классифицировать корень: instruction gap / context gap / execution gap
3. Если **execution gap** — перевести запись в секцию FIXED со статусом `WON'T_FIX` и пометкой "известное ограничение модели", skill не править
4. Если **instruction/context gap** — переходить к anti-bloat check

#### Шаг D2: Anti-bloat check (обязательно)
Перед правкой ответить на 5 вопросов из rca-protocol.md:
1. Покрыто ли уже существующим правилом? → усилить формулировку, не клонировать
2. Локальное или глобальное правило? → SKILL.md vs `~/.claude/CLAUDE.md`
3. Можно ли вынести в reference? → если чеклист 3+ пунктов → в `references/*.md`
4. Не дублирует ли соседний skill? → искать общего родителя, shared reference
5. Не устарело ли старое правило? → при добавлении нового — проверить устаревание

#### Шаг D3: Минимальная правка
1. Резервная копия правимого skill в `references/backups/{name}-YYYY-MM-DD.md`
2. **Edit**, не Write
3. Формулировка как инвариант, не как исключение из конкретного инцидента
4. Один дефект — один патч (кроме явных кластеров)

#### Шаг D4: Валидация и закрытие
1. Прочитать изменённый skill — проверить размер (≤200 строк) и валидность frontmatter
2. Если размер превысил лимит — откатить, перенести в references
3. Перевести запись в `skills-errors.md` из OPEN в FIXED с описанием фикса и anti-bloat отчётом
4. Записать итог в `references/improvement-log.md`

### Контракт результата (Режим D)
- `Обработано OPEN-записей` — число
- `Кластеры` — сгруппированные общей причиной дефекты
- `RCA-корни` — распределение instruction / context / execution gap
- `Применённые правки` — список skills и сути изменений
- `WON'T_FIX` — execution gaps с обоснованием
- `Anti-bloat отчёт` — что уплотнено вместо добавления
- `FIXED-записи` — ссылки в skills-errors.md

### Режим E: Регулярный аудит (автоматический)

Активируется по команде `/claude-booster weekly-audit`, `/claude-booster auto-audit` или scheduled task. Анализирует свежие чаты + ERRORS.md проектов и применяет правки без явной команды на каждый инцидент.

#### Шаг E0: Конфигурация
- **Период по умолчанию:** последние 7 дней (или явно указанный диапазон).
- **Проекты:** content-service, LMS, SPW, tg-bot (читать из `~/.claude/CLAUDE.md` § Проекты).
- **Триггер для автоправки:** найдены **≥2 эпизода** одного класса ошибки в одном skill — применить правку. Единичные находки → запись в OPEN секцию `references/skills-errors.md`, не правка.

#### Шаг E1: Сбор сигналов (параллельно)
1. Прочитать ERRORS.md каждого проекта — выписать **новые** записи (после последнего прогона `improvement-log.md`).
2. Запустить параллельно 4 Explore-агента (по проектам) на JSONL-чаты периода. Каждый ищет: повторы из ERRORS, новые классы, эффективность последних правок.
3. `git log --since=...` для сверки code vs spec/ERRORS.
4. **Контур усиления скиллов (knowledge-pipeline, внутренней задаче R5 + bucket_marker внутренней задаче follow-up).** За каждый день окна прочитать НЕПОМЕЧЕННЫЕ записи корзины `skill_boost`:
   `cd ~/projects/knowledge-pipeline && python -m content_analyzer.bucket_marker --list --bucket skill_boost --date YYYY-MM-DD --marker skill_audit`
   (marker `skill_audit` — постоянное имя этого контура; уже обработанные в прошлых прогонах записи не возвращаются повторно — не читать сырые `.jsonl` напрямую, чтобы не переобрабатывать старые находки). Плюс свежие ТЗ `skill_boost/YYYY-MM-DD.md` для контекста. Это **проактивный** источник (лучшие практики/находки по ИИ-инфраструктуре из внешних источников), НЕ error-сигнал. Каждый item: `summary` + `tags` + `global_uid`. Отобрать те, что напрямую относятся к существующим skills (Claude Code, промптинг, MCP, агенты, оценка). Если корзины нет за период или список пуст — пропустить без ошибки.

#### Шаг E2: Кластеризация и RCA
1. Сгруппировать находки по корневой причине (`references/rca-protocol.md`).
2. Кластеры с ≥2 эпизодами → автоправка через Режим D.
3. Единичные → OPEN запись в `skills-errors.md`.
4. **Предложения из skill_boost (E1.4)** — обрабатывать ОТДЕЛЬНО от error-кластеров: это не дефекты, а идеи усиления. Правило: применять автоправкой только если предложение (а) конкретно, (б) ложится на существующий skill/reference в рамках его назначения (не расширяет scope), (в) не противоречит текущим правилам. Иначе — записать одной строкой в раздел отчёта «Предложения из skill_boost» для решения оператора, не править молча. Anti-bloat check (rca-protocol) обязателен. **После вынесения решения по item'у — пометить обработанным С реальным исходом** (внутренней задаче: `processed_by` фиксирует не только факт рассмотрения, но и что стало с находкой — иначе воронка потребления `funnel_report.py` не отличает применённое от отброшенного), чтобы не всплывал в следующем прогоне и чтобы исход был виден в аналитике:
   `python -m content_analyzer.bucket_marker --mark --bucket skill_boost --date YYYY-MM-DD --marker skill_audit --uid <global_uid> --outcome <applied|deferred|rejected> [--note "..."]` (можно несколько `--uid` за вызов, или `--uids-file` со списком). Три случая решения → три значения `--outcome`:
   - правка внесена в skill/reference → `--outcome applied`
   - вынесено оператору (не автоправка, требует его решения) → `--outcome deferred`
   - отбраковано (не подошло по правилу (а)/(б)/(в) выше) → `--outcome rejected`
   `--note` — краткое обоснование, добавлять когда решение неочевидно из `summary` находки (не обязателен, если причина и так ясна из формулировки предложения).

#### Шаг E3: Применение правок
1. Для каждого кластера применить **Режим D** (5 Whys → instruction/context/execution → anti-bloat → минимальная правка).
2. **Ограничение auto-режима:** только Edit существующих references/skills. Создание новых файлов требует явного approval оператора через `AskUserQuestion`.
3. Backup всех изменяемых файлов в `references/backups/{name}-YYYY-MM-DD.md`.

#### Шаг E4: Отчёт + operator handoff
1. Записать в `references/improvement-log.md` (раздел `YYYY-MM-DD — Автоматический аудит`).
2. Если найдены S1/S2 кластеры требующие новых references — выдать handoff по [operator-handoff-rules.md](references/operator-handoff-rules.md): «N кластеров требуют создания новых файлов. A) я создаю по согласованным шаблонам / B) ты создашь / C) пропустить».
3. Повторы паттернов 3+ раза подряд → эскалация: явный маркер `**ESCALATION:** skill=<name>, repeats=N, нужен ручной аудит`.

### Контракт результата (Режим E)
- `Период` — даты анализа
- `Проекты` — какие проанализированы + размеры чатов
- `Сигналы из ERRORS.md` — новых записей по проектам
- `Кластеры` — корневые причины + число эпизодов
- `Автоправки` — список skills/references + краткое описание
- `OPEN записи` — единичные находки в skills-errors.md
- `Предложения из skill_boost` — идеи усиления из корзины knowledge-pipeline (применённые автоправкой / вынесенные оператору)
- `Эскалации` — повторы паттернов / нужны новые файлы
- `Operator handoff` — что требует ручного решения

### Автоматизация (scheduler)

Регулярный запуск Режима E через `mcp__scheduled-tasks__create_scheduled_task` или Windows Task Scheduler. Рекомендуемое расписание: **каждый понедельник 09:00**. Конфиг команд: см. [auto-audit-config.md](references/auto-audit-config.md).

## Правила качества
- **Пробел в покрытии скиллов → предложить новый скилл чипом, не терпеть молча.** Если в работе выявлен класс задач, для которого профильного скилла НЕТ, и класс **повторяющийся, а не разовый** (та же работа всплывёт снова) — предложить оператору создание отдельным чипом (`spawn_task`): Режим C (контентные скиллы) или `anthropic-skills:skill-creator` (остальные). Предложить, не создавать молча. Разовая задача — не повод для скилла (anti-bloat: лишний скилл хуже отсутствующего — он размывает авто-подбор). Правило-близнец в `~/.claude/CLAUDE.md` § «Автоподбор skills», ветвь 4.
- **«Проверено» ≠ «правдоподобно объясняет наблюдение».** Прежде чем писать в реестр/лог слово «проверено», ответить: какой эксперимент **развёл бы** мою версию и альтернативную? Не ставил такого — это гипотеза, так и писать.
