# Реестр skills — ролевая модель для планировщиков

Используется `spec-writer`, `change-plan-architect`, `tech-spec-composer`, `ceo-review`, `eng-review` для распределения задач плана по skills.

Планировщик обязан: (1) прочитать этот реестр при составлении плана, (2) для каждой задачи плана указать ответственный skill, (3) для переходов между этапами явно указать skill-вызов.

## Pipeline

```
spec-writer → change-plan-architect → tech-spec-composer → executor-lite/pro → review-gate → ship
                                                                         ↑
                                          context-auditor (в любой точке) │
                                                                         │
                                               response-quality-coach (при дефекте)
                                                                         │
                                                               claude-booster (RCA → улучшение skill)
```

## Роли по категориям

### Планирование и спецификация
| Skill | Роль | Когда вызывать |
|---|---|---|
| `/spec-writer` | Размытая задача → спецификация с критериями готовности | Вход pipeline: постановка задачи |
| `/change-plan-architect` | План внедрения с зависимостями и блокерами | После spec, перед реализацией |
| `/tech-spec-composer` | ТЗ для внешних агентов-исполнителей с явным контекстом | Если задача делегируется внешнему агенту |
| `/ceo-review` | Переосмысление плана (3 режима охвата) | Сомнения в scope или архитектуре продукта |
| `/eng-review` | Инженерный обзор плана (техлид) | Перед фиксацией технического плана |
| `/architect-system-analyst` | Полный архитектурный аудит (AS-IS→TO-BE→ADR) | Системные изменения, migrations, новые компоненты |

### Ревью и контроль качества
| Skill | Роль | Когда вызывать |
|---|---|---|
| `/review-gate` | Финальный PASS/FAIL перед merge (10-мерный аудит) | merge-gate |
| `/pr-review` | Pre-landing ревью PR (SQL/LLM-безопасность, Fix-First) | Ревью диффа против base-ветки |
| `/techlead-code-reviewer` | Строгое code-review production-readiness (S1/S2/S3) | Критичный production-код |
| `/context-auditor` | Сверка артефакта с исходными целями | Любая точка pipeline при риске scope-drift |

**Границы review-skills** (не путать):
- `pr-review` — **pre-landing** (до merge), Fix-First, мелкие правки прямо в diff
- `techlead-code-reviewer` — **строгий PASS/FAIL** с блокирующими находками, production-готовность
- `review-gate` — **независимый merge-gate**, финальное решение, 10 размерностей аудита

### QA (матрица: домен × режим)
| Домен | fix-and-commit | report-only |
|---|---|---|
| **Browser функционал** (MCP Claude_Browser/claude-in-chrome) | `/qa` | `/qa-only` |
| **Browser дизайн/UI** (MCP Claude_Browser/claude-in-chrome) | `/qa-design-review` | `/plan-design-review` |
| **Code/stack** (Python/Node/SQL) | `/qa-fix` | — |

Выбирай по двум осям: **что тестируем** (UI в браузере vs код в репо) и **что делаем с найденным** (чиним или только отчёт).

## Правила распределения для планировщиков

1. **Один skill = одна задача плана.** Не миксовать ответственности.
2. **Переходы через gates** (spec-gate → execution-gate → review-gate) — явно указывать skill на каждом gate.
3. **Контекстный уровень** — minimal (executor-lite), standard (executor-pro), full (architect-system-analyst).
4. **Если задача не ложится в реестр** — сигнал пользователю, что нужен новый skill (вызвать claude-booster).
5. **Не дублировать роли**: внутри QA-матрицы выбирать одну ячейку (домен × режим). Не запускать `/qa-design-review` и `/plan-design-review` на одну задачу — это пара fix/report. Аналогично для `/qa` + `/qa-only`.
6. **Cross-reference**: при вызове skill указывать входной артефакт из предыдущего skill (spec → план → ТЗ → код → ревью).
