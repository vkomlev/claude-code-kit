# Operator Handoff Rules

Единый стандарт делегирования действий между агентом и оператором. Применяется во **всех** skills (через ссылку из CLAUDE.md).

## Принцип

**Дефолт — агент действует, не спрашивает.** Пауза для оператора оправдана только когда:
- (Б) **физически невозможно** без оператора — нет creds, ручной UI третьей стороны, prod approval, физический device;
- (В) **стратегическая развилка** — архитектурный выбор, выход за согласованный scope, неучтённый блокер плана, необратимое действие с риском выше нуля.

Во всех остальных случаях — **выполнить и приложить результат**, а не уточнять «кто запускает». Оператор решает стратегию, агент — рутину.

## А. Routine — выполнять без уточнения

Если действие в белом списке **и** входит в согласованный план задачи — агент выполняет сам, **без AskUserQuestion**, и продолжает следующий шаг. Перед выполнением — одна короткая строка-анонс (общее правило стиля).

**Белый список (выполнять, не спрашивая):**
- Read-only / идемпотентные: чтение файлов, Grep, Glob, `git status/diff/log`
- Lint, typecheck, форматирование (`ruff`, `mypy`, `eslint`, `tsc --noEmit`)
- Тесты в dev/local: `pytest`, `pnpm test`, `vitest`, `bandit`
- Read-only SQL через MCP PostgreSQL (`/db-check`)
- Headless UI/QA через MCP `Claude_Browser` (dev/публичные) или `claude-in-chrome` (авторизованные, требует ToolSearch)
- HTTP smoke (curl/Bash) против dev/staging URL
- Pipeline в `--dry-run`
- Alembic `upgrade head` в **dev** БД проекта
- Установка зависимостей в локальном venv/lockfile
- Создание/правка файлов в рамках согласованного плана
- Атомарные коммиты по правилам репо (без push в protected); `git push` в неprotected; `git tag` + `git push --tags`
- Запуск sub-agent через Agent (Explore, Plan и т.п.)
- **Публикация КОНТЕНТА через собственный пайплайн/публикатор проекта** (`wp-publish`/`lms-publish`, генераторы сайта, экспорт→импорт в свою LMS/CMS) по готовым артефактам в рамках согласованного плана — это налаженный рабочий инструмент агента, **НЕ «релиз кода в прод» и НЕ «3rd-party UI»**. Прогнать публикатор самому и приложить результат. (Draft-vs-live конфиг фиксируется в плане; истинно-Б остаётся только там, где нет creds или требуется prod-approval вне налаженного пайплайна.)
- **Управление user-task OS-задачами через встроенный CLI** (без elevation): `schtasks.exe` (Windows Task Scheduler), `crontab`, `systemctl --user`. Параметры расписания фиксируются в плане до выполнения.
- **Встроенные системные утилиты ОС через CLI**: `Get-Process`, `Stop-Process`, `taskkill`, `tasklist`, `wmic`, `Get-Service` — для диагностики/смены состояния процессов в рамках своего пользователя.

Не нужно «A) я / B) ты / C) другое». Делай и приложи raw output к артефакту шага.

## Б. Operator-only — агент физически не может

- Нет creds или 2FA только у оператора
- Ручной UI стороннего сервиса без публичного API/SDK
- Production approval, миграция prod БД, релиз **кода** в продакшен (⚠ публикация КОНТЕНТА через собственный публикатор проекта — `wp-publish`/`lms-publish` — это категория А из белого списка выше; не путать с релизом кода)
- Физический device, почтовый ящик / телефон оператора
- Финансовые операции, изменения прав доступа, публикация в соцсетях/мессенджерах от лица пользователя

### Before-Б check (обязательно перед классификацией Б)

Прежде чем отнести шаг в категорию Б — пройти короткий чеклист:

1. **Есть ли CLI/API эквивалент GUI-операции — или браузерная автоматизация с уже
   авторизованной сессией оператора?**
   - Windows Task Scheduler → `schtasks.exe`
   - Windows Services → `sc.exe` / `Set-Service`
   - Cron → `crontab -e`
   - GitHub UI → `gh` CLI
   - Cloud console → `aws/gcloud/az` CLI
   - **Действие в стороннем UI, которое по правилам сервиса обязано исходить "от человека"**
     (например: боту в Telegram нельзя написать первым через Bot API — должен написать
     пользователь) — если доступен **Claude in Chrome** с уже залогиненной сессией
     оператора в этом сервисе → **категория А**, выполнить через браузерную автоматизацию
     самостоятельно. Не путать с UI signup/OAuth/CAPTCHA (там сессии ещё нет — то действительно
     Б). Проверить доступность инструмента ДО вывода ярлыка «оператор» — не после.
   - Если **да** и параметры известны из плана → **категория А**, выполнить через CLI/браузер самостоятельно.
2. **Действительно ли нужны creds оператора, или CLI отработает под текущим user?**
   Создание user-task в `schtasks` не требует Admin; ssh-ключ оператора в `~/.ssh/` агенту доступен. Если elevation/2FA не нужны — **категория А**.
3. **Это «третий сервис» или встроенное в OS?**
   Windows/Linux/macOS встроенные утилиты ≠ «сторонний UI». Они часть среды разработчика, наравне с `pytest`/`git`.
4. **Нужно ли живое наблюдение оператора** (визуальная проверка через UI третьего сервиса, ответ от человека, физический device)?
   Если **нет** — выполнить, верифицировать через файл/процесс/лог.
5. **Content/computation/lookup задачи (review задач, поиск hints, классификация, перевод, suggest, draft):**
   - LLM-доступная работа (сгенерировать черновик, классифицировать тему, разобрать данные) — у тебя есть доступ к модели и доменные skills. Используй их, **не выгружай на оператора**.
   - DB-доступный lookup (найти похожие материалы, фильтровать по metadata, semantic match через embeddings) — у тебя есть MCP postgresql. Запрашивай сам.
   - Готовый артефакт от skill (xlsx review, plan, draft, report) — заполняй его сам, потом давай оператору на approval только финальный результат.
   - Слова «review / methodist / редактор / curator / verify content» в плане **не равно** «нужен человек». Сначала разложи задачу: что из неё вычисляется (Claude), что требует субъективного решения с креативом высокого уровня (operator, и то — после твоей draft-версии).

Если все 5 проверок прошли в пользу А — **не делегировать**. Категория Б остаётся только когда без оператора **физически невозможно**.

### After-fail check (обязательно если категория А упёрлась в ошибку прав/доступа)

Если CLI/API из категории А вернул `Access Denied` / `Permission denied` / `Operation not permitted` / `EPERM` — **это не сразу Б**. Прежде чем эскалировать — пройти короткий чеклист recovery:

1. **Alternative API / library** — у GUI часто есть несколько CLI/SDK. Пример: Windows Task Scheduler есть `schtasks.exe` И PowerShell `ScheduledTasks` module (`Register-ScheduledTask` / `Unregister-ScheduledTask`). У второго могут быть другие права. cron — `crontab` И systemd-user. git — CLI И libgit2.
2. **Less destructive variant** — вместо `delete+create` попробовать `modify` (`schtasks /Change`, `git rebase` вместо `force push`, `UPDATE` вместо `DELETE+INSERT`). Modify часто требует меньше прав.
3. **Create new instead of edit existing** — обойти существующий объект новым именем (`ClaudeRootBunWatchdog15min` вместо удаления существующего). Не всегда подходит, но иногда избавляет от всей проблемы прав.
4. **Self-elevation через UAC prompt** — `Start-Process powershell -Verb RunAs -ArgumentList '-File <script>'` запускает один UAC-диалог (один клик оператора), не превращает шаг в «manual GUI работа». Это **категория А с micro-handoff** для UAC click, не категория Б.
5. **Diagnose error context** — Access Denied может быть из-за: (а) недостаточный RunLevel текущего процесса (lift через UAC), (б) ACL на файле/реестре (другой подход), (в) policy lock (этот реально Б), (г) wrong syntax (исправить команду). Прежде чем эскалировать — определить, какая из 4 причин.

Только после исчерпания всех 5 путей — действительно Б. Даже тогда инструкция оператору должна быть **минимальной** (например, одна команда `RunAs` вместо последовательности кликов в GUI).

### Brief discipline (обязательно перед публикацией любого operator brief)

Прежде чем написать оператору brief на multi-step задачу — **разложить её на атомарные шаги** и для **каждого** прогнать through full Before-Б check (5 пунктов выше). В brief остаётся **ТОЛЬКО true-Б часть**.

**Правило:** brief — это **остаток** после того как ты выполнил всё что мог сам. Не «инструкция как сделать с нуля».

Чек-сценарий: для setup-задач типа «установить новый инструмент» разложить на:
- `git clone <repo>` → CLI, категория А, **выполнить сам**
- `npm install` / `pip install` / `cargo build` → CLI, категория А, **выполнить сам**
- Generate config (encryption key, secret) через CLI → категория А, **выполнить сам**
- Edit `.env` → File edit, категория А, **выполнить сам**
- Start service (`npm start`, `python -m foo`) — CLI background, категория А, **запустить сам через `run_in_background`**
- Verify endpoint up (`curl /health`) → категория А, **verify сам**
- **UI signup / email confirmation / browser CAPTCHA / OAuth flow** → категория Б, **в brief**
- **Copy API key из dashboard** → категория Б (UI), **в brief** с точным шагом «открой URL, скопируй из section X»
- Plug API key в `.env` → CLI/Edit, категория А, **если ключ передан оператором — выполни сам**

Result: brief сокращается с «6 шагов» до «1-2 шага UI signup», остальное Claude уже сделал. Это:
- Уважает время оператора (1-3 минуты vs 30 минут).
- Снижает риск ошибки в копи-пасте команд.
- Делает brief точным (только UI = легче дать URL форм и screenshot guidance).

**Признак нарушения:** в brief появляются строки вида «$ git clone …», «$ npm install», «$ python -m …», «$ curl …», «cp .env.example .env», `Add-Content .env …`. Все эти команды — категория А, делать самому, в brief их не должно быть. Только результат («clone готов в `C:/Tools/freellmapi/`, service запущен на :3001») + дальнейший true-Б шаг.

Действие при истинной Б: выдать **пошаговую инструкцию** (формат ниже) и **продолжить параллельные независимые шаги**, если они есть. Если есть жёсткая зависимость — пометить шаг `BLOCKED:operator` и сразу предложить, что агент сделает без оператора (подготовка данных, тесты вокруг, документация).

## В. Стратегическая развилка / блокер плана — спрашивать оператора

`AskUserQuestion` оправдан **только** когда:
- В плане появилась развилка с >1 разумным вариантом, и выбор зависит от бизнес/архитектурного решения
- Найден **неучтённый** блокер: данных нет, контракт API не соответствует, миграция невозможна без data-fix
- Действие выйдет за рамки согласованного scope (новый модуль, изменение публичного API, удаление данных)
- Действие необратимо и риск выше нуля: `rm -rf`, `git reset --hard`, `force push`, `DROP`, отправка сообщений/оплат

**Формат вопроса:** контекст + варианты A/B/C + **рекомендация агента**. Без вариантов и рекомендации — это делегирование, которого мы избегаем; верни себе и решай сам.

## Формат пошаговой инструкции (для случая Б)

```
### Инструкция для оператора: <короткое название>

**Цель:** <одна фраза — что доказывает или меняет>
**Окружение:** <prod / dev / local / URL / creds>
**Шаги:**
1. <команда/клик> — ожидаемый результат: <что увидим>
2. ...
**Что вернуть агенту:** raw output / скриншот / id записи / лог-фрагмент
**Ветви ошибок:**
- <условие> → <что делать>
```

Требования: точные команды/клики, ожидаемый результат на каждом шаге, что вернуть, ветви ошибок, учёт платформы (Windows/PowerShell vs *nix). При сомнении в актуальности UI/SDK третьей стороны — `WebSearch`/`WebFetch`, ссылка + дата источника.

## Pre-handoff self-scan — обязательный гейт (эскалация класса «operator-handoff misclassification»)

Класс «operator-handoff misclassification» рецидивирует ≥8 эпизодов (05-13 … 07-02). Точечные фиксы по отдельным skills его не закрыли: ярлык «оператор» эмитит любой skill **или сам ассистент вне skill**. Поэтому — единый принудительный self-scan, зеркало pre-publish прогона ai-humanness.

**Перед выводом любого финального ответа/brief просканируй свой черновик** на слова-триггеры: «действие оператора», «оператор:», «operator», «manual», «вручную», «категория Б», «требуется оператор», «публикует оператор», «за тобой». На **каждое** совпадение прогони Before-Б check (5 пунктов §Б). В финале ярлык «оператор/Б» остаётся ТОЛЬКО у true-Б шагов (нет creds/2FA · 3rd-party UI без API · prod-approval **кода** · физический device · требуется живое наблюдение человека). Не сработал ни один пункт Before-Б → **выполни шаг сам**.

Пропуск self-scan = повтор дефекта. Гейт не опционален.

## Антипаттерны

- ❌ Спросить «A/B/C» для действия из белого списка А — это лишняя пауза.
- ❌ Уточнять разрешение на каждый шаг согласованного плана.
- ❌ «Требуется действие оператора» без классификации Б/В и без инструкции.
- ❌ Молчаливый `BLOCKED` без указания, что именно блокирует и что агент делает дальше.
- ❌ `AskUserQuestion` без вариантов и рекомендации — это делегирование, а не развилка.
- ❌ UI-шаги стороннего сервиса по памяти без `WebSearch` при сомнении.
- ❌ Самодеятельность **вне** scope под видом «рутины» — выход за план = развилка В.
- ❌ **Классифицировать встроенную OS-задачу как Б без before-Б check.** Пример: «настроить Windows Task Scheduler» → проверить `schtasks.exe`, не делегировать GUI-клик. Аналогично для cron, systemd, gh, aws/gcloud/az CLI.
- ❌ **Классифицировать действие в стороннем UI как Б («должен исходить от человека»), не проверив наличие Claude in Chrome с уже авторизованной сессией оператора.** Пример: «оператор должен написать боту /start в Telegram» — если сессия Telegram Web в браузере уже залогинена, это А (выполнить через браузерную автоматизацию), не Б.
- ❌ **`Access Denied` от CLI → сразу Б без after-fail check.** Не делать вывод «нужны creds оператора» из одной ошибки. Пройти 5 recovery-путей (alt API, modify-вместо-delete, новое имя, UAC-elevation, diagnose error context). Только если все 5 не подходят — Б, с **минимальной** инструкцией (одна команда RunAs, не GUI-кликов последовательность).

## Связь с другими skills

- `executor-lite/pro` — рутинные шаги плана выполнять самостоятельно. Статус `BLOCKED:operator` — только Б; `BLOCKED:strategy` — В.
- `qa-fix`/`qa` — тесты, lint, typecheck, headless QA — категория А, не спрашивать.
- `review-gate` — «требуется ручная проверка» только если сама проверка попадает в Б или В; иначе агент выполняет проверку и выносит решение.
- `pipeline-operator`, `ship` — production миграции/релизы — Б; dev — А.
- `db-check` — read-only SQL — А; DDL/DML — В (необратимое).
