# Бриф проекта — обязательный артефакт ревью

Используется skills `/ceo-review` и `/eng-review` для сохранения контекста исследования
в файл проекта. Без брифа последующие исполнители (`executor-pro`, `review-gate`,
`context-auditor`) не имеют доступа к решениям, принятым на этапе ревью плана.

## Расположение и именование

- **Каталог:** `docs/briefs/` в корне текущего проекта (создать если отсутствует)
- **Имя файла:** `{slug}.md`, где `slug` =
  1. имя текущей git-ветки (если репозиторий) — нормализованное (`/` → `-`, нижний регистр), без префикса `feature/`/`fix/`
  2. либо короткий kebab-case slug задачи если ветки нет
- **Один бриф на одну задачу/ветку.** При повторном ревью той же ветки — Edit, не Write
- **Кодировка:** UTF-8 без BOM. Без эмодзи (см. `encoding-guard`)

## Frontmatter

```yaml
---
task: <однострочное описание задачи>
branch: <имя ветки или "no-branch">
review_skill: ceo-review | eng-review
mode: РАСШИРЕНИЕ | УДЕРЖАНИЕ | СОКРАЩЕНИЕ | БОЛЬШОЕ | МАЛЕНЬКОЕ
created: YYYY-MM-DD
updated: YYYY-MM-DD
status: in-progress | finalized
plan_ref: <ссылка/путь на план или "встроен в бриф">
---
```

## Секции (заполнять инкрементально по ходу ревью)

```markdown
# Бриф: {task}

## 1. Метаданные
- Цель задачи: <1-2 строки>
- Заинтересованные skills (исполнители): <executor-lite/pro, fastapi-api-developer, ...>
- Связанные документы: <CLAUDE.md, TODOS.md, спецификация>

## 2. Системный аудит (ceo-review: PRE-REVIEW; eng-review: опционально)
- git log (последние N релевантных коммитов): <bullet-list>
- Затронутые TODO из TODOS.md: <bullet-list со ссылками>
- Известные болевые точки в области: <bullet-list>
- Предыдущие циклы ревью на ветке: <ссылки/выводы или "нет">

## 3. Шаг 0 — вызов охвата
- Правильная ли это проблема: <ответ>
- Реальный бизнес-результат: <ответ>
- Что произойдёт если не делать: <ответ>
- Существующий код, частично решающий задачу: <bullet-list файлов/модулей>
- Идеальное состояние через 12 мес (только ceo-review): <1-2 абзаца>
- Минимальный набор изменений (только eng-review): <bullet-list>
- Выбранный режим/охват и обоснование: <строка>

## 4. Ключевые находки по разделам
Заполняется по 1-2 строки на каждый пройденный раздел ревью.
Только КРИТИЧЕСКИЕ ПРОБЕЛЫ и ПРЕДУПРЕЖДЕНИЯ — не дублировать чат.

- Архитектура: <находки>
- Ошибки и обработка: <число пробелов, критические>
- Безопасность: <находки>
- Данные и граничные случаи: <находки>
- Качество кода: <находки>
- Тесты: <пробелы>
- Производительность: <находки>
- Наблюдаемость: <пробелы>
- Деплой: <риски>
- Долгосрочная траектория: <обратимость, долг>

## 5. Открытые решения
Что осталось нерешённым после ревью — точка входа для следующей сессии.
- <решение 1>: <варианты A/B/C, текущий выбор или null>

## 6. TODO-кандидаты
Из ревью предложено добавить в TODOS.md (не дублировать TODOS.md, только список идентификаторов):
- <TODO-ID или 1-строчное описание>: <решение пользователя — добавлен/отложен/выполнен>

## 7. Артефакты
Ссылки на тяжёлые артефакты, не вкладываемые в бриф:
- Диаграммы: <путь или inline-секция>
- Реестр режимов сбоя: <путь>
- Тест-план: <путь — для eng-review>
```

## Правила заполнения

1. **Инкрементальность.** После PRE-REVIEW и Шага 0 — Write скелет (секции 1-3).
   После каждого пройденного раздела ревью — Edit соответствующей строки в секции 4.
   В конце ревью — Edit секций 5-7.
2. **Anti-bloat.** Бриф ≠ полная стенограмма ревью. Сохраняем только то, что
   нужно следующему исполнителю для понимания контекста — без чата восстановить
   решения, режим и приоритеты.
3. **Без переписывания плана.** Если план уже лежит в `docs/specs/` или подобном —
   ставить ссылку в `plan_ref`, не копировать содержание.
4. **Обновление, а не клонирование.** Повторное ревью той же ветки = Edit
   существующего брифа, добавляя секцию `## История ревизий` с датой и delta.
5. **Финализация.** В конце ревью переключить `status: finalized` и обновить `updated`.
6. **Если каталог `docs/` отсутствует** — создать `docs/briefs/`. В проектах без
   `docs/` (мелкие скрипты) — фиксировать это и спросить оператора:
   A) создать `docs/briefs/` / B) разместить рядом с задачей / C) пропустить бриф
   (последнее — только при явном согласии оператора, с пометкой в чате).

## Валидация перед записью

- Каталог `docs/briefs/` существует или создан
- YAML frontmatter валиден (закрыт `---`)
- Кодировка UTF-8 без BOM
- Имя файла соответствует slug-правилам
- При обновлении — `updated` совпадает с сегодняшней датой
