# RCA-протокол для улучшения skills

Единый протокол: перед любой правкой skill-инфраструктуры применить 5 Whys + anti-bloat check. Паттерн согласован с cursor-booster и codex-booster.

Вход: запись OPEN из `skills-errors.md`.
Выход: правка skill + запись FIXED или решение WON'T_FIX.

## Шаг 1: 5 Whys

Пять уровней "почему" от симптома до корня. Каждый ответ должен быть конкретным — без "потому что плохо инструктирован".

Пример:
> Симптом: `/spec-writer` не указал критерии готовности
> 1. Почему не указал? → В output contract не было поля "Критерии готовности"
> 2. Почему не было? → Шаблон спеки не требует этого явно
> 3. Почему не требует? → Skill создавался как MVP, критерии считались очевидными
> 4. Почему считались очевидными? → В команде раньше их держали в голове
> 5. Почему держали в голове? → Не было формального гейта spec→execution
>
> Корень: отсутствие формального гейта spec→execution.

**Корень называет механизм, а не место, где он вылез.** «Нет онбординга Python-среды» —
это симптом на языке инцидента; «на Windows политика исполнения блокирует `.ps1`-шимы» —
механизм. Первое чинит один курс, второе — класс. Проверка перед Шагом 2: подставить в
свой корень другой инструмент / другой проект — если корень перестал звучать осмысленно, он
привязан к инциденту и 5 Whys не доведены (см. «Тест на обобщение», Шаг 4).

## Шаг 2: Классификация корня

Одно из трёх (остальное — не поводом править skill):

| Класс | Что значит | Куда править |
|---|---|---|
| **instruction gap** | Skill не содержит нужной инструкции | SKILL.md или references/ |
| **context gap** | Skill не подтянул нужный контекст (файл/реестр/история) | Шаг 0 / references / импорты |
| **execution gap** | Инструкции правильные, модель не исполнила | НЕ править skill. Зафиксировать как limit, эскалировать модель/пересмотреть пример |

## Шаг 3: Anti-bloat check (обязательно перед правкой)

Перед тем как добавить инструкцию в SKILL.md, ответить:

1. **Покрыто ли уже существующим правилом?**
   - Если да — не добавлять. Возможно, усилить формулировку существующего, не клонировать.

2. **Это локальное правило или глобальный инвариант?**
   - Локальное (касается только этого skill) → в SKILL.md
   - Глобальное (касается всех skills) → в `~/.claude/CLAUDE.md` или `references/standard.md`

3. **Можно ли вынести в reference-файл?**
   - Если это чеклист из 3+ пунктов → в `references/*.md`, в SKILL.md — 1 строка-указатель
   - SKILL.md ≤200 строк; всё сверх — в references

4. **Не дублирует ли соседний skill?**
   - Если да — искать общего родителя, выносить в shared reference или глобальный CLAUDE.md

5. **Убрало ли старое правило чтобы добавить новое?**
   - При добавлении нового инварианта — проверить, не устарело ли старое

## Шаг 4: Минимальная правка

Правило: **минимальное изменение, покрывающее корень**.

- Один дефект — один патч
- Edit (не Write) для существующих skills
- Формулировка как инвариант, не как исключение
- Пример: не "если юзер в Russia, не использовать X", а "использовать X только там, где юзер явно попросил"

### Тест на обобщение (обязателен — от него зависит, будет ли рецидив)

Anti-bloat (Шаг 3) защищает от правила, которое **слишком широко**. Этот тест — от
противоположной ошибки: правила, которое **слишком узко**. Нужны оба; ловится только
второй, и именно он возвращается рецидивом.

Прежде чем записать правку, ответить: **что в моей формулировке механизм, а что —
случайная деталь инцидента?**

1. Правило называет **инструмент или место** инцидента (Python, venv, этот курс, эта
   таблица, этот эндпоинт)? → сузил. Спросить: **где ещё работает тот же механизм?**
   Переписать на механизм, инцидент оставить примером — не наоборот.
2. Контрольный вопрос: **«та же поломка придёт через другой инструмент — правило
   сработает?»** Нет → правило не готово, независимо от того, насколько точно оно
   описывает случившееся.
3. Правило-заплатка на один инструмент = гарантия, что завтра заведут «а4» на соседний.
   Плодить по инструменту — тот самый bloat, только отложенный.

**Прецедент.** Фикс внутренней задаче записан как «нет онбординга локальной среды
**Python** на Windows» (venv/activate/pip) — на языке инцидента. Механизм был шире:
*на Windows политика исполнения блокирует любой `.ps1`-шим, а bash-инструкция либо
падает, либо тихо делает не то*. Через месяц тот же корень пришёл через `npm` на
Node-курсе — правило молча не сработало, ученик встал на 2-м уроке фундамента флагмана.
Симптом был пофикшен, класс — нет.

### Механизация (обязательна, когда правило уже существовало)

Тест на обобщение выше страхует от слишком узкой формулировки. Этот шаг — от другой
ошибки: **чинить формулировкой то, что формулировкой не чинится.**

Контрольный вопрос перед правкой: **правило уже существовало и было доступно в момент
нарушения?** (документ лежал в контексте, инвариант записан в SKILL.md / CLAUDE.md /
DESIGN.md). Если да — усиление текста даст рецидив. Корень не в том, что правило
непонятно сформулировано, а в том, что **между правилом и действием нет проверки**.

**Порог: второе нарушение одного правила = сигнал на механизацию, а не на
переформулировку.** Считать нарушения, а не убедительность формулировки.

Форма проверки — по слою, где живёт нарушение:

| Слой | Механизм |
|---|---|
| Код проекта | тест-страж или правило линтера (падает в регрессии) |
| Момент коммита | pre-commit hook |
| Поведение агента | PreToolUse-хук (`~/.claude/hooks/`) |
| Данные | ограничение схемы / валидатор при записи |

Механизировать нельзя (нет объективного признака) → **сузить область применения
правила**, а не повторять его громче: правило, которое нельзя проверить, живёт ровно до
первой спешки.

**Прецеденты.** `DESIGN.md` запрещал форматировать даты в компонентах — за пять волн
один и тот же агент внёс три разных формата, имея документ в контексте; закрылось
правилом линтера, не редакцией запрета. Класс «мёртвый маршрут» всплывал пять раз и
закрылся тестом-стражем. Оба гейта в `CLAUDE.md` (`db_write_gate`, `skill_engage_gate`)
заведены по той же причине: «правило держалось только на дисциплине и почти всегда
обходилось».

## Шаг 5: Валидация

После правки:
1. Прочитать SKILL.md — проверить что он не разбух
2. Прогнать по `references/audit-checklist.md`
3. Если размер превысил лимит — откатить и перевнести в references
4. Записать в `skills-errors.md` → FIXED с описанием фикса и anti-bloat отчётом

## Стоп-условия

Не править skill, если:
- Причина — execution gap (модель не смогла следовать правильной инструкции)
- Инцидент единичный и не воспроизводится
- Правка потребует добавить >10 строк в SKILL.md → искать reference-решение
- Не прошёл 5 Whys (симптом не доведён до корня)

## Пример применения

Дефект: `/executor-pro` не запустил тесты перед commit.

5 Whys:
1. Почему не запустил? → В Workflow "запуск тестов" был обобщённым, без явного gate
2. Почему без gate? → Считалось частью "smoke check"
3. Почему смешано? → Исходно executor-pro = "выполни, потом smoke"
4. Почему не разделили? → Не было инцидента с пропущенным тестом
5. Почему не было? → Был — но не логировался

Корень: **instruction gap** — нет явного gate "tests pass before commit". Дополнительно: **context gap** — отсутствовал реестр ошибок для обучения.

Anti-bloat check:
- Есть ли уже правило? Частично в `review-gate`, но review-gate после commit
- Локальное? Да, для executor-pro
- Вынести в reference? Нет, одна строка достаточно
- Дубль? Нет — в review-gate другой контекст (pre-merge, не pre-commit)

Фикс: в `executor-pro/SKILL.md` → Правила качества: "Никогда не commit без зелёного pytest".
Размер прирост: 1 строка. Приемлемо.
