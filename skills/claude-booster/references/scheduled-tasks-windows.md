# Регулярные задания в Windows Task Scheduler — грабли этой машины

Применять при заведении ЛЮБОГО планового задания (чек данных, аудит, триггер-напоминание),
а не только того, ради которого файл написан. Конкретный конфиг недельного аудита скиллов —
`auto-audit-config.md`; здесь то, что общее для всех заданий.

**Инвариант.** Задание, которое «зарегистрировано и Ready», ещё ничего не значит. Пока не
увидел `LastTaskResult = 0` **и** побочный эффект (строку в логе, файл, сообщение) — задание
не работает. Ручной прогон скрипта этого не доказывает: он идёт в другом окружении.

---

## 1. Планировщик стартует в `C:\Windows\System32`

Не в каталоге скрипта и не в корне проекта. Любой относительный путь внутри — считается от
`System32`, куда обычному пользователю писать нельзя.

Как проявилось: обёртка звала python-скрипт → импорт модуля БД тянул конфиг,
а тот создаёт каталоги `uploads/*` **от текущего каталога** →
`PermissionError: [WinError 5] 'uploads'`. Импорт падал ещё до первой строки логики.

**`$PSScriptRoot` не спасает** — он про то, где скрипт *лежит*, а не откуда *запущен*.
В начале обёртки:

```powershell
$repo = Split-Path -Parent $PSScriptRoot
Set-Location $repo
```

Правило шире одного проекта: **любой код, который создаёт/читает пути относительно cwd,
ломается под планировщиком.** Импорт чужого конфига — тоже такой код, хотя по вызову этого
не видно.

## 2. `$ErrorActionPreference = "Stop"` убивает обёртку на выводе в stderr

С `Stop` вывод внешней программы в stderr PowerShell превращает в **терминирующую** ошибку.
Скрипт умирает на строке вызова — до логирования. Симптом: **пустой лог при ненулевом коде**,
то есть ровно там, где ты рассчитывал прочитать причину.

```powershell
try {
    $prev = $ErrorActionPreference
    $ErrorActionPreference = "Continue"   # stderr питона — это данные, не падение
    $out = & $py $script --quiet 2>&1
    $code = $LASTEXITCODE
    $ErrorActionPreference = $prev
} catch {
    Add-Content -Path $log -Value "$stamp  ОШИБКА обёртки: $_" -Encoding UTF8
    exit 2
}
```

**Тело обёртки — всегда в `try/catch` с записью `$_` в лог.** Иначе диагностика сводится к
гаданию: причина не доживает до места, где её пишут.

## 3. Коды выхода: смерть обёртки ≠ содержательная находка

Если скрипт отдаёт `1` на «нашёл проблему», а обёртка на своей смерти тоже отдаёт `1` —
`LastTaskResult = 1` читается как «проверка отработала и что-то нашла», хотя она не
запускалась. Такое легко уводит диагностику в сторону.

Разводить с самого начала: `0` — чисто, `1` — содержательная находка, `2` — сбой самой
проверки. И обёртка обязана возвращать **свой** код, а не наследовать чужой.

## 4. История заданий на этой машине ВЫКЛЮЧЕНА

`Microsoft-Windows-TaskScheduler/Operational` → `IsEnabled = False`. Совет «посмотри History
задания» здесь не работает — там пусто.

Диагностика вместо History: **воспроизвести условия запуска**, а не запускать «как удобно» —
из `C:\Windows\System32`, тем же пользователем, тем же `powershell -NoProfile
-ExecutionPolicy Bypass -File <абсолютный путь>`. Разница между «работает у меня» и «падает
под планировщиком» почти всегда в cwd, окружении или профиле.

Проверять факт запуска:
```powershell
Get-ScheduledTaskInfo -TaskName "<имя>"   # LastRunTime, LastTaskResult, NextRunTime
```

## 5. `schtasks` из Git Bash: подмена путей и кавычки

- **`MSYS_NO_PATHCONV=1` обязателен**, иначе Git Bash превращает `/create` в
  `C:/Program Files/Git/create` и команда падает с «неверный параметр».
- **Экранированные кавычки внутри `/tr` ломаются**: `\"путь\"` сохраняется как `путь""` —
  PowerShell ищет файл с кавычками в имени и выходит с `1`. Если в пути нет пробелов —
  кавычки не нужны вовсе.
- После регистрации **прочитать, что реально сохранилось**, а не верить «Успех»:
  ```
  MSYS_NO_PATHCONV=1 schtasks /query /tn "<имя>" /fo LIST /v
  ```
  Вывод в cp866 — декодировать (`cp866`), иначе кириллица нечитаема.

## 6. `.ps1` с кириллицей — только UTF-8 **с BOM**

Без BOM PowerShell 5.1 читает исходник как cp1251 и портит кириллицу на этапе разбора —
до всякого вывода; `[Console]::OutputEncoding` это не лечит (другой слой). Проверка:
`open(p,'rb').read(3) == b'\xef\xbb\xbf'`. Инструмент Write BOM не ставит — дописывать
отдельным шагом (`encoding='utf-8-sig'`).

## 7. Куда задание смотрит: dev или прод

`.env` проектов может указывать на dev (напр. `localhost`, прод закрыт от скриптов), а
проверять надо то, что видят пользователи. Прод-DSN брать явным override, а **сам скрипт
обязан первой строкой печатать хост и базу** — dev и прод расходятся по данным сильно, и
перепутать их легко.

## 8. Проверка «на живом» перед сдачей

Не «запустил скрипт руками — работает», а:
1. `schtasks /run` (или `Start-ScheduledTask`) — запуск **самим планировщиком**;
2. `Get-ScheduledTaskInfo` → `LastTaskResult = 0`;
3. побочный эффект на месте (строка в логе с новым временем);
4. `NextRunTime` — ожидаемый.

Типичная ловушка: два независимых дефекта (cwd + EAP) маскируют друг друга; каждый по
отдельности даёт одинаковый симптом «код 1, лог пуст».
