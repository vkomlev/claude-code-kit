# Consistency Mode — сквозной аудит UX-консистентности живого многоэкранного продукта

## Когда включать этот режим (вместо дефолтного Full/Quick/Deep)

- Продукт УЖЕ живой и построен: не маркетинговый лендинг, не «первое впечатление с нуля».
- Многоэкранный: 5+ экранов/разделов одного продукта/портала.
- Экраны собирались ИНКРЕМЕНТАЛЬНО — разными сессиями/чипами/спринтами, не одним проходом.
- Дизайн-система уже фактически есть (пусть не задокументирована) — придумывать её с нуля не нужно.
- Задача — не «как выглядит на первый взгляд», а «совпадают ли одинаковые по смыслу вещи на разных экранах».

Триггерные формулировки оператора: «сквозной аудит», «консистентность между экранами», «продукт/портал вырос быстро», «разные чипы/сессии собирали разные экраны».

**Auto-detect:** включать этот режим, если явно указан `--consistency` ИЛИ запрос описывает уже живой построенный продукт с несколькими экранами и НЕ упоминает «с нуля» / маркетинг / лендинг / первый запуск. Сообщить о выборе режима оператору одной строкой перед стартом.

## Чем отличается от дефолтного прохода

| | Full/Quick/Deep (по умолчанию) | Consistency |
|---|---|---|
| Фокус | впечатление НОВОГО посетителя | глаз человека, который уже пользуется продуктом и переходит между экранами |
| Design system | извлекается с нуля (Phase 2) | читается существующий DESIGN.md/токены один раз как baseline — дальше не переоткрывается |
| AI Slop / First Impression | полная оценка (Phase 1, категория 9) | сворачивается в 1 строку — не относится к внутреннему инструменту/порталу |
| Единица анализа | страница | ПАТТЕРН (тип элемента), повторяющийся на разных экранах |
| Результат | оценки A-F по 10 категориям | Матрица консистентности + список находок дрейфа |
| Фиксы | как обычно (Phase 7-11) | те же фазы, но фиксы группируются по ТИПУ паттерна — унифицировать все вхождения одного паттерна одним коммитом логичнее, чем чинить экран за экраном |

## Методология (6 шагов)

Основана на практике design system audit (инвентаризация → категоризация → выявление несоответствий → оценка визуальной консистентности → доступность → документация) и эвристике Nielsen Norman Group №4 «Consistency and standards» — расхождения накапливаются именно там, где над продуктом работали разные люди/сессии в разное время.

### Шаг 1 — Interface Inventory (инвентаризация экранов)

Обойти все экраны/разделы в скоупе (дашборд, списки, карточки деталей, поиск, лента, уведомления, настройки и т.д.). На каждом экране зафиксировать screenshot + список UI-паттернов на нём — не пересказ содержимого, а какие ПОВТОРЯЮЩИЕСЯ элементы встречаются: как показана дата/время, как показан статус, как выглядит пустое состояние, как оформлен primary-action, как показан заголовок раздела/«где я», как оформлена карточка/строка списка.

### Шаг 2 — Pattern Clustering (кластеризация по типу паттерна)

Перегруппировать собранное не по экранам, а по ТИПУ паттерна. Для каждого типа — таблица «экран → как реализовано → скриншот». Обязательный минимальный набор типов (дополнять по продукту):

- Дата/время (относительное «5 мин назад» vs абсолютное «27.07.2026, 18:07» vs смешанное)
- Статус/бейдж (цвет + текст + форма)
- Пустое состояние (текст + иконка/иллюстрация + primary action)
- Состояние загрузки (skeleton/spinner/blank)
- Состояние ошибки (текст + возможность повторить)
- Заголовок раздела / breadcrumbs / способ показать «где я»
- Первичное действие (кнопка: расположение, формулировка, цвет)
- Строка списка / карточка (отступы, разделители, иконки)
- Пагинация / подгрузка («Показать ещё» vs бесконечная прокрутка vs страницы)
- Терминология для одного и того же понятия (см. Шаг 6)

### Шаг 3 — Drift Scoring (оценка дрейфа)

Для каждого типа паттерна: если один и тот же смысл показан на разных экранах >1 явно разным способом — это находка «дрейф». Severity:

- **P0/P1** — путает пользователя или показывает «сырые» данные (необработанный ISO-timestamp, необработанный enum-код) — это баг восприятия, не оформление.
- **P1/P2** — расхождение заметно при обычном использовании (разный формат даты, разный визуальный язык статус-бейджей).
- **P2/P3** — расхождение малозаметно, косметика (разный интервал отступов, разный стиль разделителя).

Не путать дрейф с обоснованной вариацией: разные типы данных законно показываются по-разному (дата встречи в календаре ≠ дата последней активности в ленте) — дрейф это когда ОДИН И ТОТ ЖЕ смысл показан по-разному, а не когда разные смыслы оформлены по-разному.

### Шаг 4 — Root-cause по времени сборки (если доступна история)

Где возможно (`git log`/`git blame` по затронутым файлам, даты задач/коммитов), отметить: паттерн собирался в рамках одной фичи/сессии (внутренне консистентен) или разные варианты появились в РАЗНОЕ время разными сессиями — это и есть механизм дрейфа: инкрементальная сборка без сквозного прохода. Помогает при Фазе 8 (Fix Loop) — паттерны с одинаковым root-cause часто чинятся одним и тем же изменением (например, вынесением общей утилиты форматирования даты).

### Шаг 5 — Navigation Topology (карта переходов)

Построить граф экранов в скоупе: откуда куда есть переход, есть ли путь «туда и обратно» для связанных экранов (список → карточка → назад), нет ли тупиков (экран без явного выхода куда-либо, кроме кнопки браузера «назад»), логично ли расположены разделы в навигации относительно частоты использования.

### Шаг 6 — Терминология и переиспользование компонентов

- **Терминология:** одно понятие называется по-разному на разных экранах («Ученики» / «Ростер», «Задание» / «Работа») — свести в таблицу синонимов, предложить единый термин.
- **Переиспользование компонентов:** для повторяющегося визуального паттерна проверить исходный код (`Grep`/`Glob` по имени компонента/CSS-классу) — реализован ли паттерн одним переиспользуемым компонентом или скопирован независимо на каждом экране (copy-paste drift). Если на N экранах N разных локальных реализаций одного и того же паттерна — это структурная причина дрейфа: фикс тогда не «поправить текст на экране X», а «вынести общий компонент/утилиту и переиспользовать её на всех N экранах» (см. Фаза 8b — предпочитать структурный фикс точечному, если находка того стоит).

## Отчёт: Матрица консистентности

Вместо (или в дополнение к) стандартным категориям A-F — таблица:

| Тип паттерна | Экран 1 | Экран 2 | Экран 3 | ... | Дрейф? | Severity |
|---|---|---|---|---|---|---|
| Дата/время | `27.07, 21:53` | `сегодня` | `2026-07-27T08:00:00+00:00` (сырой ISO) | ... | ДА — 3 варианта | P0 (сырой ISO) |
| Статус-бейдж | зелёный pill | цветной текст без фона | ... | ... | ДА | P2 |

Плюс раздел **«Что сделано хорошо, не трогать»** — переиспользуемые паттерны, уже консистентные на нескольких экранах (не только находки, но и ориентир для унификации остального — не переписывать компонент, который уже переиспользуется правильно).

Находки из Матрицы дополнительно оформляются в стандартном формате Findings (impact/category/page) для совместимости с остальным отчётом skill'а — Матрица консистентности идёт отдельным разделом ДО обычного списка находок, как наглядная сводка.

## Фиксы для findings дрейфа (Фаза 8, консистентность-специфика)

- Точечный фикс (поправить один экран) годится только для косметики (P3) или когда паттернов реально мало.
- Для P0-P2 дрейфа с >2 вхождениями — предпочесть структурный фикс: вынести общую утилиту/компонент (форматирование даты, компонент статус-бейджа) и переиспользовать на всех затронутых экранах ОДНИМ коммитом на паттерн, а не N коммитами на экран. Это всё ещё «один коммит — один фикс» в терминах Фазы 8c, просто единица фикса — паттерн, а не экран.
- Если структурный фикс выходит за рамки CSS-only (Правило 16 «CSS-first») — это ожидаемо для консистентность-фиксов (унификация формата даты — это логика, не стили); повышенный риск компенсировать более частым self-regulation checkpoint (Фаза 8f) — не ждать 5 фиксов, проверяться после каждого структурного изменения.

## Ограничения

- Этот режим не отменяет Phase 1 (First Impression) и категорию «AI Slop» там, где продукт публичный/маркетинговый — для внутреннего инструмента/портала эти секции сворачиваются в 1 строку каждая («не применимо — внутренний инструмент») вместо полного прохода.
- Не решать самостоятельно, является ли расхождение осознанным дизайн-решением или дрейфом — при сомнении спросить оператора, а не додумывать.
- Navigation Topology и проверка переходов требуют реальных кликов в браузере (`computer{action:"left_click"}` + сравнение screenshot до/после), а не догадок по карте роутов.
