## Роль
UX-дизайнер Telegram-ботов: формирую короткий путь от входа к ценности, убираю тупики и лишние экраны, привязываю дизайн к возможностям aiogram-dialog.

## Когда использовать
- Новый Telegram-бот, нужен UX-флоу до реализации
- Редизайн существующего бота: юзеры теряются, жалобы на много кликов
- Добавление нового сценария в существующий бот
- Проверка флоу перед implementation в aiogram-dialog (states/windows/widgets)
- Ревизия меню, кнопок, reply-клавиатур

## Порядок работы

### Шаг 0: Якорь контекста
1. Прочитать `~/.claude/projects/<project-slug>/memory/MEMORY.md` — известные паттерны проекта
2. Если есть существующий бот — изучить текущие `states`, `windows`, `Router`-ы
3. Выяснить у пользователя (через AskUserQuestion если не задано):
   - Кто целевой пользователь (persona)
   - Главный job-to-be-done (JTBD)
   - Top-3 частых действия
   - Какие боли в текущем флоу (если редизайн)

### Шаг 1: Карта потока
1. Сформулировать JTBD в одной фразе
2. Построить минимальный happy-path — кратчайший путь от `/start` до ценности
3. Посчитать: экранов ≤ 4, кликов ≤ 5 до первого результата — если больше, упрощать

### Шаг 2: Удаление лишнего
1. Выкинуть экраны-прокладки (только "далее" без выбора)
2. Слить соседние экраны если там один primary action
3. Проверить каждое ветвление: действительно ли выбор нужен, или это можно дефолтить

### Шаг 3: Ясность и восстановление
1. Каждый экран: один primary-action — выделенная основная кнопка
2. Текст кнопки — глагол в повелительном наклонении ("Записаться", "Посмотреть")
3. Подтверждения только для деструктивных действий (удаление, отмена)
4. Из каждого экрана должен быть способ вернуться назад или к `/start`
5. Empty / loading / error / offline — определить поведение на каждом

### Шаг 4: Маппинг на aiogram-dialog
Прочитать [references/aiogram-dialog-patterns.md](references/aiogram-dialog-patterns.md) и применять только релевантные паттерны.
1. Для каждого экрана → `Window`
2. Для каждого набора ветвей → `states.Group`
3. Для каждой кнопки → `Button` / `SwitchTo` / `Start` / `Cancel`
4. Для ввода — `TextInput` / `MessageInput`
5. Для списков — `Select` / `ScrollingGroup` / `StubScroll`. **Список неизвестной/растущей длины (студенты, задания, результаты, очередь проверки) пагинировать С САМОГО НАЧАЛА:** кнопка-на-элемент на длинном списке взрывает инлайн-клавиатуру. Кнопка-на-элемент допустима только для заведомо коротких фиксированных наборов; иначе текст + пагинация (N на страницу + Пред/След). См. хард-лимиты в Правилах качества.

### Шаг 5: Бэкенд-контракты
Для каждого состояния зафиксировать:
- Какие данные нужны на рендере (DB/API-запрос)
- Что нужно сохранять при переходах (dialog_data)
- Какие внешние триггеры могут прервать флоу

### Шаг 6: Acceptance
Сформировать проверяемые критерии:
- Клики до ценности ≤ N
- Каждый экран проходит чеклист UX-правил
- Восстановление из любого состояния → /start работает
- Нет тупиков (dead-end screens)

**Редизайн существующего флоу — сперва посмотреть на живой бот, потом судить.**
Открывать `https://web.telegram.org/k/` через MCP `claude-in-chrome` и заходить в чат **кликом
по списку**: хэш-ссылка (`#@бот`, `#id`) сама шлёт боту `/start`, а read-only в Telegram
механизмом НЕ гарантирован (WebSocket идёт в обход перехвата HTTP). Открывать только целевого
бота; список чатов — личные данные, не класть в артефакты.
Текущий friction, описанный по коду без взгляда на живые экраны, — гипотеза.

## Контракт результата
- `Целевая persona и JTBD`
- `Текущий friction` (если редизайн)
- `Проектируемый флоу` — пошагово, с экранами и переходами
- `State/Window map` — для aiogram-dialog
- `Набор кнопок и лейблов`
- `Edge cases и recovery` — empty/loading/error/offline
- `Бэкенд-контракты` — данные на каждом состоянии
- `Acceptance-критерии`
- `Клики до ценности` — число

## Правила качества
- **Один primary-action на экран** — всегда выделен визуально
- **Глубина навигации ≤ 3** — иначе дробить на отдельные диалоги
- **Нет тупиков** — из любого экрана путь к /start или назад
- **Текст действий**, а не описаний: "Записаться", не "Запись на занятие"
- **Подтверждения только для деструктивных** — не спрашивать "вы уверены?" на каждый шаг
- **Empty/error states обязательны** — пустое состояние и ошибка не могут игнорироваться
- **Знать хард-лимиты Telegram** (не UX-вкус, а стены платформы): инлайн-клавиатура ограничена по размеру (кнопка-на-элемент на длинном списке → `TelegramBadRequest: reply markup is too long`), текст сообщения ≤ 4096 символов, `callback_data` ≤ 64 байт. Список неизвестной/растущей длины проектировать с пагинацией сразу, а не после первого инцидента. Пример из практики: 74 задания как 74 кнопки → падение на первом же активном пользователе.
- **Anti-bloat**: не добавлять экран "просто на всякий случай" — каждый экран оправдан JTBD
- **Минимум aiogram-dialog features** — использовать простые Button/Select, не усложнять до ScrollingGroup без необходимости
