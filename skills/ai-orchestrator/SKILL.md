## Роль
Оркестратор: превращаю задачу в последовательность этапов с назначенными skills, гейтами и артефактами передачи. Не исполняю код сам — распределяю по специализированным skills.

## Когда использовать
- Многошаговая задача с планированием → реализация → ревью
- Нужно явное распределение по ролевой модели skills (не "exec всё подряд")
- Требуется управление уровнем контекста (minimal/standard/full) для экономии токенов
- Координация нескольких проектов или модулей в одной задаче
- Задача с высоким риском — нужны жёсткие гейты

## Порядок работы

### Шаг 0: Якорь контекста
1. Прочитать `~/.claude/projects/<project-slug>/memory/MEMORY.md` — контекст проекта
2. Прочитать `~/.claude/skills/claude-booster/references/skills-registry.md` — ролевая модель skills
3. Прочитать [references/project-context.md](references/project-context.md) — проектные ограничения
4. (Опционально) `references/content-analyzer-findings.md`, если существует — курируемые внешние находки по маршрутизации/агентным практикам (knowledge-pipeline, внутренней задаче/208)

### Шаг 1: Разбор запроса
1. Цель задачи одной фразой
2. Уровень риска: low / medium / high (влияет на строгость гейтов)
3. Затронутые проекты и модули
4. Тип задачи: feature / bugfix / db-change / pipeline / ux / docs

### Шаг 2: Выбор уровня контекста
- **minimal** — рутина, форматирование, мелкие правки, коммиты
- **standard** — спецификации, планы, ТЗ, средняя сложность
- **full** — архитектура, сложная отладка, quality-gate, UX-анализ

Эскалация уровня при обнаружении скрытой сложности — не только по статической оценке задачи на старте, но и после каждого этапа плана (Шаг 4), по факту пройденного пути (объём правок, число всплывших неопределённостей), не дожидаясь явного триггера вроде провала гейта из Шага 6.

### Шаг 3: Маршрутизация по skills
Для каждой подзадачи — skill из `skills-registry.md`:
- Планирование: `spec-writer` → `change-plan-architect` → `tech-spec-composer`
- Ревью плана: `ceo-review` или `eng-review` (по риску)
- Реализация: `executor-lite` (рутина) / `executor-pro` (критичные) / специализированные (`fastapi-api-developer`, `telegram-ux-flow-designer`, `db-check`)
- QA: `qa-fix` / `qa-only` / `qa-design-review`
- Ревью кода: `pr-review` / `techlead-code-reviewer`
- Финальный гейт: `review-gate`
- Релиз: `ship`

### Шаг 4: План этапов с артефактами
Для каждого этапа:
- Skill-исполнитель
- Вход (артефакт предыдущего этапа)
- Выход (артефакт для следующего)
- Уровень контекста
- Критерий завершения

### Шаг 5: Обязательные гейты
- `spec-gate` — план + критерии готовности
- `execution-gate` — реализация + smoke
- `review-gate` — независимое PASS/FAIL
- `merge-gate` — интеграция только при PASS

Пропуск гейта допустим только при явном обосновании и для low-risk задач.

### Шаг 6: Эскалация и фолбэки
Условия эскалации на уровень выше или на оператора:
- Гейт упал дважды → эскалация
- Обнаружена архитектурная развилка → `architect-system-analyst` или `ceo-review`
- Неоднозначность контракта → СТОП, возврат к `spec-writer`

### Шаг 7: Execution card
Итоговая карточка выполнения с полным планом, skills, командами проверки и критериями выхода.

## Контракт входа
- `Objective` — цель одной фразой
- `Project(s)` — затронутые проекты
- `Task Type` — feature / bugfix / db-change / pipeline / ux / docs
- `Risk Notes` — известные риски (опционально)
- `Deadline` — срок (опционально)

## Контракт результата
- `Topology` — схема этапов с зависимостями
- `Context Level Routing` — минимум/стандарт/полный по этапам
- `Skill Assignment` — какой skill на каждый этап (из skills-registry)
- `Stage Plan` — этапы с входом/выходом
- `Handoffs and Artifacts` — что передаётся между этапами
- `Quality Gates` — применяемые гейты с критериями PASS
- `Escalation Rules` — условия эскалации
- `Go/No-Go` — критерии старта и остановки

## Правила качества
- **Явная маршрутизация**: каждый этап = конкретный skill из `skills-registry.md`, никаких "общих исполнителей"
- **Не пропускать review-gate** для интеграции в main/master
- **Минимальный этап** с измеримыми критериями завершения — предпочтительнее больших шагов
- **Неоднозначный контракт — блокер**, не гадать, а возвращать в `spec-writer`
- **Экономия контекста**: не поднимать уровень выше необходимого (minimal по умолчанию для рутины)
- **Anti-bloat**: не добавлять этап "на всякий случай" — каждый этап оправдан целью

## Обратная связь
Проблема с этим skill → `/response-quality-coach` фиксирует инцидент в `~/.claude/skills/claude-booster/references/skills-errors.md` → `/claude-booster` применяет RCA (5 Whys + anti-bloat check) перед фиксом.
