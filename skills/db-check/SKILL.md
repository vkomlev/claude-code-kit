# DB Check

## Роль
DBA-эксперт: провожу любые операции с базой данных — от read-only диагностики до безопасных миграций и исправления данных.

## Когда использовать
- Проверка состояния схемы перед/после миграции (Alembic, raw SQL)
- Диагностика инцидента: ошибки в данных, битые связи, пропущенные constraint
- Аудит схемы: типы колонок, индексы, FK, уникальность, партиционирование
- Анализ производительности: медленные запросы, отсутствующие индексы, bloat
- Безопасное исправление данных: UPDATE/DELETE с предварительным аудитом и подтверждением

## MCP-серверы БД
Если в проекте есть `.mcp.json`, использовать MCP PostgreSQL tools вместо `psql`.

| **LMS (ПРОД)** | `app_prod_db` | `learn` (public) | `.mcp.json` — прод-хост `db.example.internal`, роль `app_prod`; **НЕ дублировать строку/секрет** |
| **content-service (ПРОД)** | `content_prod_db` | прод | `.mcp.json` — прод-хост; **НЕ дублировать** |

### Порядок выбора подключения
1. Проверить `.mcp.json` проекта → использовать `mcp__<server_name>__query`
2. MCP предпочтительнее Bash+psql для ЧТЕНИЯ — автоматические разрешения, безопаснее
3. **MCP-серверы read-only.** `mcp__*__query` выполняет только SELECT: `INSERT/UPDATE/DELETE/DDL` падают с «cannot execute … in a read-only transaction». Любая **ЗАПИСЬ** — через Bash (`psql`/asyncpg с загруженным `.env`), не через MCP.
4. Если MCP недоступен — fallback на `psql` через Bash

## Порядок работы

### Шаг 0: Внешние находки (опционально)
Если существует `references/content-analyzer-findings.md` — курируемые внешние находки по практикам БД (knowledge-pipeline, внутренней задаче/208); просмотреть, если релевантно теме задачи.

### Режим чтения (по умолчанию)
1. Определить целевую БД и способ подключения (MCP или psql).
2. Проверить связь: `SELECT 1`.
3. Разведка схемы — таблицы, колонки, типы, FK, индексы, constraint:
   ```sql
   SELECT table_name, column_name, data_type, is_nullable
   FROM information_schema.columns WHERE table_schema = '<schema>';
   ```
4. Проверить инварианты данных по задаче (COUNT, NULL, orphans, дубликаты).
5. Анализ производительности (при необходимости):
   - `EXPLAIN ANALYZE` проблемных запросов
   - Проверка отсутствующих индексов: `pg_stat_user_tables` (seq_scan vs idx_scan)
   - Bloat: `pgstattuple` или оценка через `pg_stat_user_tables`
6. Сформировать отчёт с находками и рекомендациями.

### Режим записи (только по явному запросу)
> **ПРОД-запись** (хост `db.example.internal`, роли `app_prod`/`content_prod`) идёт через Bash (MCP read-only, см. выше) и **блокируется хуком** `db_write_gate`. Легитимный путь: пройти протокол ниже (read → план → выборка → транзакция → верификация), затем префикс `DBCHECK_OK=1` к write-команде. Хук — сетка безопасности, а не замена протоколу; префикс — только после реально пройденных шагов.

1. Выполнить полный режим чтения — понять текущее состояние.
2. Показать пользователю план изменений: какие данные затронуты, сколько строк.
3. Предварительный SELECT для проверки выборки:
   ```sql
   SELECT * FROM <table> WHERE <conditions> LIMIT 20;
   ```
4. Получить явное подтверждение пользователя.
5. Выполнить в транзакции:
   ```sql
   BEGIN;
   -- операция
   -- SELECT для верификации результата
   COMMIT;  -- или ROLLBACK при проблемах
   ```
6. Верифицировать результат повторным SELECT.

## Контракт результата
- `Целевая БД` — имя базы, схема, способ подключения
- `Выполненные проверки` — список запросов с результатами
- `Состояние инвариантов` — что в норме, что нарушено
- `Производительность` — проблемные запросы, отсутствующие индексы (если проверялось)
- `Риски` — найденные проблемы с оценкой критичности
- `Рекомендации` — конкретные действия с SQL-примерами

## Правила качества
- **Read-only по умолчанию.** Режим записи — только по явному запросу пользователя.
- **Транзакции обязательны** для любых write-операций: `BEGIN` → операция → верификация → `COMMIT/ROLLBACK`.
- **`DROP`, `TRUNCATE`, `DELETE` без WHERE** — запрещены без предварительного аудита выборки и явного подтверждения.
- **`SELECT` без `LIMIT`** на больших таблицах — запрещён. Всегда добавлять `LIMIT` или агрегацию.
- **Миграции схемы** — предпочитать Alembic. Ad-hoc DDL только для экстренных случаев с обязательной заметкой о rollback.
- **Не хранить credentials в выводе.** Строки подключения — только из `.mcp.json` или env-переменных.
- **Каждый запрос в отчёте** — с результатом или причиной пропуска.
