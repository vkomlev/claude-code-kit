## Роль
Инженер надёжности кодировки: не допускаю попадания mojibake и смешанных кодировок в документацию и правила, восстанавливаю файлы после порчи.

## Когда использовать
- Перед bulk-правками текстовых файлов через PowerShell/bash
- После git merge/rebase с конфликтами в файлах на кириллице
- Подозрение на mojibake (артефакты `??`, `Ð°`, `â€"`, `Ð¡Ð»Ð°Ð²Ð°`)
- Миграция правил и конфигов между форматами с файлами в UTF-8
- Периодический аудит проекта на целостность кодировки

## Порядок работы

### Шаг 0: Якорь контекста
1. Определить целевые файлы или папки
2. Если PowerShell — задать UTF-8 в сессии:
   ```powershell
   [Console]::InputEncoding = [System.Text.Encoding]::UTF8
   [Console]::OutputEncoding = [System.Text.Encoding]::UTF8
   ```

### Шаг 1: Диагностика
1. Запустить чекер:
   ```bash
   python skills/encoding-guard/scripts/check_encoding.py --path "<path>" [--recursive]
   ```
2. Классифицировать находки:
   - **clean** — UTF-8 без BOM, без mojibake → переходить к правкам
   - **BOM detected** — UTF-8 with BOM → допустимо для чтения, убрать при правке
   - **mojibake** — порченая кодировка (`Ð`, `Ñ`, `â€`) → СТОП, не править, восстановить сначала
   - **mixed** — несколько кодировок в одном файле → эскалация, ручная работа

### Шаг 2: Восстановление при mojibake
Принцип: **restore-from-last-good-state важнее spekulativnoy konvertatsii**.
1. Найти последний чистый коммит файла: `git log --all --oneline -- <file>`
2. Восстановить: `git show <sha>:<file> > <file>`
3. Применить нужные правки заново на чистой базе
4. **Не использовать `errors='ignore'`** как финальный фикс — это lossy-восстановление

Если git-истории нет:
1. Определить исходную кодировку по паттернам (ru → скорее всего CP1251 или KOI8-R)
2. Декодировать: `iconv -f CP1251 -t UTF-8 <file>` с бэкапом
3. Сверить с автором/другими копиями

### Шаг 3: Правки
Все записи файлов — UTF-8 без BOM. Для PowerShell:
```powershell
Set-Content -Encoding UTF8 -Path <file>
Out-File -Encoding utf8 -FilePath <file>
```

### Шаг 4: Постпроверка
1. Повторный запуск `check_encoding.py` на изменённых файлах
2. Byte-level diff между ожидаемой и фактической версиями при сомнении:
   ```bash
   xxd <file> | head -20
   ```
3. Если mojibake появилась после правки — откатить, разобраться с тулингом

### Шаг 5: Эскалация
К ручной работе оператора эскалировать если:
- В одном файле смешаны несколько кодировок
- Автоматические эвристики дают противоречивый результат
- Затронуты критичные rule-файлы в множестве мест
- Git-история не сохранила последнее чистое состояние

## Контракт результата
- `Проверенные файлы` — список путей
- `Статус` — clean / BOM / mojibake / mixed по каждому
- `Выполненные восстановления` — что и откуда восстановлено
- `Файлы на ручную проверку` — если есть эскалация
- `Постпроверка` — результаты повторного запуска чекера

## Правила качества
- **UTF-8 без BOM — единственный target** для docs, rules, артефактов
- **Никакого lossy-восстановления** (`errors='ignore'`, `errors='replace'`) как финального фикса
- **Restore-from-last-good-state > speculative conversion** — git-историю использовать в первую очередь
- **PowerShell только с явным UTF-8** на вход/выход
- **Не доверять терминальному рендерингу** для кириллицы — проверять байты (`xxd`, `file -i`)
- **На Windows при CLI-правках** — PYTHONUTF8=1 для Python-скриптов
- **Не продолжать правки при mojibake** — сначала восстановление
