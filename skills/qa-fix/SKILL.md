# /qa-fix: Тест → Исправление → Проверка

## Роль
QA-инженер и баг-фикс инженер: тестирую кодовую базу, исправляю баги атомарными коммитами, перепроверяю и выдаю отчёт до/после.

## Когда использовать
- Перед мержем фича-ветки — полный прогон тестов + исправления
- После рефакторинга — проверить что ничего не сломалось
- Инцидент в продакшене — найти и починить первопричину
- Новый проект / onboarding — оценить текущее здоровье кодовой базы
- После миграции БД — проверить schema drift и целостность данных

## Параметры

| Параметр | По умолчанию | Пример |
|----------|-------------|--------|
| Уровень  | Стандартный  | `--quick`, `--exhaustive` |
| Охват    | Весь проект  | `Фокус на модуле оплаты` |
| Стек     | Авто-детект  | `--python`, `--node`, `--sql` |

**Уровни определяют что исправляется:**
- **Быстрый:** Исправить только критические + высокие
- **Стандартный:** + средние (по умолчанию)
- **Исчерпывающий:** + низкие/косметические

**Если на фиче-ветке без конкретного охвата:** Автоматически войти в **diff-aware режим** (см. ниже).

---

## Порядок работы

1. **Шаг 0** — якорь контекста + подготовка (memory, реестр ошибок, рабочее дерево)
2. **Шаг 1** — определить охват тестирования (diff-aware или полный режим)
3. **Шаг 2** — запуск тестов и сбор базовых метрик
4. **Шаг 3** — детектирование стека
5. **Шаг 4** — статический анализ по стекам (Python / Node-React / SQL-DB / FastAPI-API)
6. **Шаг 5** — классификация проблем по приоритету (P0/P1/P2/P3)
7. **Шаг 6** — итеративное исправление с атомарными коммитами
8. **Шаг 7** — финальный прогон тестов
9. **Шаг 8** — итоговый отчёт
10. **Шаг 9** — closed-loop обновление реестра ошибок

Детали каждого шага — ниже.

## Шаг 0: Якорь контекста + Подготовка

### Восстановление контекста
1. Прочитать `~/.claude/projects/{project-dir}/memory/MEMORY.md` (если есть).
2. Найти последние JSONL-беседы проекта — извлечь acceptance criteria из спека/ТЗ.
3. Использовать acceptance criteria как **дополнительные тест-кейсы**: если критерий не покрыт тестом — отметить в отчёте.

### Загрузка реестра ошибок
4. Прочитать `{project}/docs/ai/ERRORS.md` — известные ошибки и prevention actions.
5. Прочитать `~/projects/IDE_booster/Docs/ai/ERRORS.md` — мастер-реестр (общие паттерны).
6. Для каждой prevention action из реестра по данному проекту — включить как **обязательную проверку**.
7. (Опционально) `references/content-analyzer-findings.md`, если существует — курируемые внешние находки по тестированию и статическому анализу (knowledge-pipeline, внутренней задаче/208).

### Подготовка рабочего дерева
Убедись что рабочее дерево чистое:
```bash
if [ -n "$(git status --porcelain)" ]; then
  echo "ОШИБКА: Рабочее дерево грязное. Закоммить или спрячь изменения перед запуском /qa-fix."
  exit 1
fi
```

Запомни начальный хеш коммита:
```bash
git rev-parse HEAD
```

## Шаг 1: Определить охват тестирования

### Diff-aware режим (автоматически на фиче-ветке):

```bash
git diff main...HEAD --name-only
git log main..HEAD --oneline
```

Определи затронутые модули/файлы из diff. Сфокусируй тестирование на них.

### Полный режим (main ветка или явный охват):

Тестировать всю кодовую базу.

## Шаг 4: Статический анализ (по стекам)

### Python-блок

```bash
# Линтинг
python -m flake8 . --max-line-length=120 --exclude=.git,venv,node_modules 2>&1 | head -50

# Типизация (strict если проект поддерживает)
python -m mypy . --ignore-missing-imports 2>&1 | head -50

# Безопасность
python -m bandit -r . -x ./venv,./tests -ll 2>&1 | head -50

# Покрытие (baseline)
python -m pytest --cov --cov-report=term-missing -q 2>&1 | tail -30

# Импортные циклы
python -c "
import importlib, sys, os
for root, dirs, files in os.walk('.'):
    dirs[:] = [d for d in dirs if d not in ('venv', '.git', 'node_modules')]
    for f in files:
        if f.endswith('.py'):
            mod = os.path.join(root, f).replace('./', '').replace('/', '.').replace('.py', '')
            try:
                importlib.import_module(mod)
            except ImportError as e:
                if 'circular' in str(e).lower():
                    print(f'CIRCULAR: {mod} — {e}')
" 2>&1 | head -20
```

### Node/React-блок

```bash
# TypeScript строгая проверка
npx tsc --noEmit 2>&1 | head -50

# ESLint
npx eslint . --ext .ts,.tsx,.js,.jsx --max-warnings=0 2>&1 | head -50

# React-специфика: неиспользуемые зависимости
npx depcheck 2>&1 | head -30

# Bundle size (если есть build)
[ -f next.config.js ] || [ -f vite.config.ts ] && npm run build 2>&1 | tail -20
```

### SQL/DB-блок

Если проект имеет MCP PostgreSQL (`.mcp.json`) — использовать MCP tools.
Если нет — fallback на `psql`.

```bash
# Alembic: текущая ревизия vs head
alembic current 2>&1
alembic heads 2>&1

# Pending миграции
alembic history -r current:head 2>&1

# Проверка что миграции не конфликтуют
alembic check 2>&1
```

**SQL-проверки через MCP или psql:**
```sql
-- Таблицы без первичного ключа
SELECT t.table_name FROM information_schema.tables t
LEFT JOIN information_schema.table_constraints tc
  ON t.table_name = tc.table_name AND tc.constraint_type = 'PRIMARY KEY'
WHERE t.table_schema NOT IN ('pg_catalog', 'information_schema')
  AND tc.constraint_name IS NULL;

-- FK без индексов (потенциально медленные JOIN)
SELECT conrelid::regclass AS table_name, a.attname AS column_name
FROM pg_constraint c
JOIN pg_attribute a ON a.attnum = ANY(c.conkey) AND a.attrelid = c.conrelid
WHERE c.contype = 'f'
  AND NOT EXISTS (
    SELECT 1 FROM pg_index i WHERE i.indrelid = c.conrelid
    AND a.attnum = ANY(i.indkey)
  );

-- Bloat: таблицы с высоким seq_scan без индексов
SELECT relname, seq_scan, idx_scan, n_live_tup
FROM pg_stat_user_tables WHERE seq_scan > 1000 AND idx_scan < 100
ORDER BY seq_scan DESC LIMIT 10;
```

### FastAPI/API-блок

```bash
# Smoke-тест: сервер запускается
timeout 10 python -c "
from importlib import import_module
app_module = None
for mod in ['app.main', 'main', 'src.main', 'app']:
    try:
        m = import_module(mod)
        if hasattr(m, 'app'):
            app_module = m; break
    except ImportError:
        continue
if app_module:
    print(f'APP FOUND: {app_module.__name__}')
else:
    print('APP NOT FOUND')
" 2>&1

# Проверка роутов: есть ли эндпоинты без документации
grep -rn "def.*(" --include="*.py" | grep -E "@(app|router)\.(get|post|put|delete|patch)" | head -20

# OpenAPI schema если доступна
curl -s http://localhost:8000/openapi.json 2>/dev/null | python -m json.tool | head -30
```

Составь список находок по категориям.

## Шаг 5: Классификация проблем по приоритету

Для каждой найденной проблемы:

```
ПРОБЛЕМА #{N}
=============
Критичность: КРИТИЧЕСКАЯ / ВЫСОКАЯ / СРЕДНЯЯ / НИЗКАЯ
Файл: {путь}:{строка}
Тип: {падение теста / ошибка типа / ошибка линтера / логический баг / производительность}
Описание: {что не так}
Предлагаемое исправление: {как исправить}
```

**Критерии критичности:**
- **КРИТИЧЕСКАЯ:** Сервис не запускается, данные повреждаются, исключение в критическом пути
- **ВЫСОКАЯ:** Тест постоянно падает, логический баг влияет на корректность
- **СРЕДНЯЯ:** Деградация производительности, некорректная обработка граничных случаев
- **НИЗКАЯ:** Предупреждения линтера, стилевые проблемы, устаревший код

## Шаг 6: Итеративное исправление

Для каждой проблемы (в порядке приоритета, в рамках выбранного уровня):

### 5a: Прочитай файл и пойми контекст
```bash
# Прочитай файл перед правкой
cat {файл}
```

### 5b: Примени исправление

Сделай целевое, минимальное исправление. Не рефакторить ради рефакторинга.

### 5c: Верификация исправления
```bash
# Запусти только релевантный тест
python -m pytest {путь_к_тесту} -v 2>&1

# Или весь набор
python -m pytest -q 2>&1 | tail -10
```

### 5d: Атомарный коммит если верифицировано
```bash
git add {исправленные_файлы}
git commit -m "fix: {описание что исправлено и почему}"
```

**Никогда не коммитить непроверенные исправления.**

### 5e: Если исправление создаёт новые падения

Откатить и переосмыслить:
```bash
git stash
```

Попробовать другой подход или поднять флаг как "требует ручного расследования".

## Шаг 9: Closed-Loop — обновление реестра ошибок

После завершения исправлений — замкнуть цикл обучения (из Codex error governance):

### 9a: Запись новых ошибок
Для каждого исправленного бага категории КРИТИЧЕСКАЯ или ВЫСОКАЯ:
```bash
# Создать docs/ai/ если нет
mkdir -p docs/ai
```
Добавить в `{project}/docs/ai/ERRORS.md`:
```
| {дата} | {S1/S2} | {PROCESS/DATA/LOGIC/INTEGRATION} | {описание} | {prevention action} |
```

### 9b: 5 Whys (для КРИТИЧЕСКИХ)
Для каждой критической ошибки — записать цепочку причин:
1. Почему случилось? → ...
2. Почему это не было поймано раньше? → ...
3. Корневая причина → instruction gap / context gap / execution gap

### 9c: Проверка соседей
Для каждого исправленного паттерна — проверить, нет ли аналогичного бага в соседних модулях:
```bash
# Пример: если нашли raw SQL date comparison без нормализации
grep -rn "now()" --include="*.py" | grep -v "venv"
```

### 9d: Prevention action
Если ошибка системная — предложить обновление skill или rule (через `/claude-booster` или `/codex-booster`).

## Правила качества

* **Минимальные исправления** — исправляй только то что нужно, не рефакторь попутно
* **Сначала верификация** — никогда не коммитить без запуска тестов
* **Атомарные коммиты** — одно исправление = один коммит
* **Прозрачность** — сообщай что не удалось исправить и почему
* **Не ломай что работает** — если исправление создаёт новые проблемы, откатить
* **Сохраняй базовые метрики** — покажи до/после для демонстрации прогресса
* **MCP предпочтительнее psql** — если проект имеет `.mcp.json`, использовать MCP tools
* **SQL безопасность** — DELETE/UPDATE без WHERE запрещены; любые write-операции через транзакции
* **Operator handoff** — применить [operator-handoff-rules.md](../claude-booster/references/operator-handoff-rules.md). Дефолт: тесты, lint, typecheck, headless QA, dev SQL, smoke — категория А, выполнять самому без AskUserQuestion. Категория Б (нет creds, prod approval, manual UI третьей стороны) — пошаговая инструкция оператору. Категория В (стратегическая развилка / необратимое действие) — `AskUserQuestion` с вариантами и рекомендацией. Молчаливое «нужна ручная проверка» — дефект отчёта.
