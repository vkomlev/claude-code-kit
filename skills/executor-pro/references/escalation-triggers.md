# Escalation triggers

При срабатывании любого триггера — **немедленно остановиться**, зафиксировать evidence и эскалировать. Не пытаться угадать или "дорешать".

## Куда эскалировать

| Класс проблемы | Цель эскалации |
|---|---|
| Архитектурное решение, границы модулей | `/architect-system-analyst` |
| Нарушение принципов кода / готовность к prod | `/techlead-code-reviewer` |
| Неоднозначный план | `/change-plan-architect` (вернуть на пересмотр) |
| Сомнение в соответствии целям | `/context-auditor` |
| Нужно расширение контекста и reasoning | переключение на **full** уровень |
| Рискованная БД-операция, DSN-ошибки | `/db-check` (перед любой правкой данных) |

## Триггеры

### T1. Scope расширился
Во время правки обнаружено, что план не закрывает реальные зависимости (недокументированные callers, скрытые контракты).

**Действие:** остановиться → вернуть задачу в `/change-plan-architect` с найденными пробелами.

### T2. Два неудачных focused fix на один класс ошибки
Gate падает, применён focused fix, gate снова падает с тем же классом ошибки.

**Действие:** собрать evidence pack:
- `command` — что запускалось
- `return code` — exit code
- `error excerpt` — ключевые строки вывода
- `evidence log path` — где полный лог

Эскалация в **full**-контекст с этим пакетом.

### T3. Cross-schema риск
Правка потенциально затрагивает схемы вне вашей рабочей схемы (особенно `public`).

**Действие:** статус `NOT_READY`. Запустить `/db-check` с фокусом на isolation. Не продолжать до явного PASS.

### T4. Windows encoding / DSN аномалии
`UnicodeDecodeError`, mojibake от сервера PostgreSQL, подозрение на сломанный DSN.

**Действие:**
1. Сначала отделить DSN-проблему от server-response encoding.
2. Проверить connectivity к maintenance DB.
3. Явно проверить существование target DB (`<ваша-target-БД>`).
4. **Не делать несколько спекулятивных фиксов за одну итерацию.**
5. После одного неудачного focused fix того же класса — эскалация в full с evidence pack (см. T2).

### T5. Неоднозначный/противоречивый план
План от `/change-plan-architect` содержит взаимоисключающие требования или пропущен критичный этап.

**Действие:** вернуть план на пересмотр. Не "интерпретировать" план самостоятельно.

### T6. Архитектурное решение в процессе
Во время реализации обнаружилось, что правильный фикс требует:
- изменения границ модулей
- нового абстрактного слоя
- изменения ownership данных между схемами/сервисами

**Действие:** остановиться, переключить задачу в `/architect-system-analyst` или `/eng-review`.

### T7. Regression test невозможно написать
Дефект не воспроизводится на том же уровне абстракции, что в проде (требует сложный fixture, внешний сервис, timing-зависимость).

**Действие:** не заменять regression test на "что-нибудь похожее". Эскалировать: либо нужен integration harness (full-контекст), либо задача разбивается на две (сначала harness, потом fix).

### T8. Шутдаун validation gates
Возникает искушение отключить gate ("временно", "не относится к задаче", "флаки").

**Действие:** запрещено. Gate либо PASS, либо эскалация. `manual/pending/not run` в обязательном gate = `NOT_READY`.

### T9. Production-affecting без evidence
Задача влияет на production (БД, публикация, внешние API), но нет реальных validation commands или evidence paths.

**Действие:** статус `NOT_READY`. Не делать handoff. Требовать evidence в `reviews/*.md` (raw outputs, rollback note).

## Формат эскалации

При эскалации сформулировать:
- **Триггер** — какой из T1–T9 сработал
- **Контекст** — что пытались сделать
- **Evidence** — raw outputs, логи, пути файлов
- **Гипотеза** — если есть (но не подменять анализ)
- **Запрос** — что нужно от целевого skill/уровня

Без evidence эскалация превращается в "разберись ты" — это не эскалация, а сброс задачи.
