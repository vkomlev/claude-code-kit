# Хуки: чем правило отличается от механизма

Здесь семь хуков Claude Code. Они делятся на два рода, и разница между ними важнее,
чем список файлов:

- **Запрещающие (`PreToolUse`)** — не дают совершить опасное действие. Это большинство.
- **Проверяющая (`PostToolUse`)** — смотрит на результат уже записанного файла. Такую
  проверку обычно забывают, а именно она даёт агенту сигнал об ошибке: агент работает
  циклом, и качество цикла определяется тем, что он узнаёт о своих результатах.

| Файл | Род | Что делает |
|---|---|---|
| `skill_engage_gate.py` | Pre | **Гейт скиллов.** Блокирует `Write`/`Edit` файла проекта, если в сессии не задействован профильный скилл. |
| `skill_routing_hint.py` | подсказка | Когда в промпте упомянут проект — называет профильные скиллы ДО работы. |
| `skill_routing.py` | — | Общая библиотека матчинга. Нужна обоим — просто лежит рядом. |
| `skill_routing.json` | — | Реестр «проект → исходники → профильные скиллы». **Настраивается тобой.** |
| `chip_tree_gate.py` | Pre | Блокирует разрушительные команды в общем рабочем каталоге: `git reset --hard`, `git clean -f`, `rm -rf node_modules`, `git stash` без указания файлов. Обход: `CHIP_SOLO=1`. |
| `index_scope_gate.py` | Pre | Не даёт коммитом без pathspec унести чужую незакоммиченную работу из общего индекса. Обход: `CHIP_SOLO=1`. |
| `artifact_check.py` | **Post** | Проверяет записанный файл: валидность JSON, порча кодировки (mojibake), frontmatter скилла, правка генерируемого файла. Обход: `ARTIFACT_CHECK_OFF=1`. |

### Упомянуты в текстах, но не входят в комплект

В пояснениях внутри хуков и скиллов встречаются имена `db_write_gate`, `id_claim_gate`,
`claim_release_check`, `staged_scope_guard`, `validate_agents`. Это хуки из боевой среды,
откуда собран комплект. Их здесь нет намеренно: они завязаны на конкретные боевые серверы
и на собственный трекер задач, у тебя работать не будут. Что они делают — и что имеет смысл
сделать по их образцу, когда дорастёшь:

- `db_write_gate` — блокирует запись в БОЕВУЮ базу, если не пройден протокол проверки.
  Самый полезный из них: цена ошибки здесь выше всего.
- `id_claim_gate`, `claim_release_check` — дисциплина работы двух и более агентов над общими
  файлами: занять ресурс перед правкой и освободить после.
- `staged_scope_guard`, `validate_agents` — то же самое на уровне git-хука `pre-commit`.

## Зачем это нужно

Правило «сначала выбери профильный скилл, потом правь код» держится только на дисциплине
модели и почти всегда обходится, если скилл не назвать явно. Гейт делает правило
исполняемым: полез в код мимо скилла → блок с подсказкой, какой скилл взять. Это главная
причина, по которой скиллы реально начинают работать, а не простаивают.

Та же логика у `artifact_check.py`, только с другой стороны цикла. Правила вроде «проверь
JSON после правки» или «следи за кодировкой» живут в инструкциях текстом — и потому
нарушаются: в конце работы контекст занят результатом, а не памяткой. Хук проверяет молча
и говорит, только когда есть что сказать.

## Как работает гейт

При каждом `Write`/`Edit` хук проверяет по цепочке (первое сработавшее — решает):
1. Файл не попал под правило проекта из `skill_routing.json` → **пропустить**.
2. Переменная окружения `SKILL_ENGAGED=1` → **пропустить** (ручной/headless обход).
3. Свежий (≤24 ч) маркер-файл `.skill-engaged-note.md` в дереве проекта → **пропустить**.
4. В транскрипте сессии уже был вызов скилла нужного домена → **пропустить**.
5. Иначе → **БЛОК** (exit 2) с текстом: какой скилл взять и как снять блок.

Домены (`engineering` / `content` / `marketing` / `infra`) важны: инженерный скилл не
снимает блок с маркетингового артефакта, и наоборот — каждый домен силансится своими
скиллами.

### Три способа снять блок
- **Задействовать скилл** — просто вызвать `/executor-lite` (или другой скилл домена).
  Это штатный путь.
- **Осознанно править напрямую** — создать файл `.skill-engaged-note.md` в дереве
  правимого файла (1–2 строки: какой скилл использован ИЛИ почему напрямую). Действует сутки.
- **Обход в окружении** — префикс `SKILL_ENGAGED=1` к команде (для headless/скриптов).

Хук **fail-open**: при ошибке разбора входа или реестра он пропускает, чтобы не ломать
работу. Но «нет сигнала о скилле» трактуется как блок — иначе гейт выродится в бездействие.

## Настройка `skill_routing.json`

Открой файл и в блоке `rules` замени два примера на свои проекты. Одно правило = один
проект (или один каталог внутри проекта). Поля:

```jsonc
{
  "name": "Мой backend-проект",        // как назвать в тексте блока
  "domain": "engineering",              // engineering | content | marketing | infra
  "root": "d:/work/my-app",             // корень проекта: НИЖНИЙ регистр, слеши вперёд
  "source_dirs": ["app", "src"],        // каталоги с кодом (пусто = всё поддерево)
  "extensions": [".py"],                // что считаем исходником
  "skills": ["executor-pro", "db-check"], // профильные скиллы (для подсказки)
  "hint": "Код -> /fastapi-api-developer, БД -> /db-check."
}
```

- `root` — обязательно нижний регистр и прямые слеши (`d:/work/my-app`), даже на Windows.
  Матчинг идёт по сегментам пути, поэтому worktree-копии проекта тоже попадают под гейт.
- `skills` в правиле — для подсказки; **блок снимает любой скилл того же домена**
  (список — в `silencing_by_domain`).
- Порядок правил важен: побеждает первое совпавшее. Частные правила ставь выше общих.

## Подключение в `settings.json`

Возьми блок `hooks` из `../settings.json.example` и **замени `ИМЯ_ПОЛЬЗОВАТЕЛЯ` на свой
домашний каталог**. Windows — команда `python "C:\Users\ТЫ\.claude\hooks\skill_engage_gate.py"`;
macOS/Linux — `python3 ~/.claude/hooks/skill_engage_gate.py`.

Хуки перечитываются на лету — перезапускать Claude Code не нужно.

## Проверить, что гейт работает

Сделай `Write` нового файла в путь, попадающий под твоё правило, без вызова скилла — должен
прийти блок с подсказкой. (Проверять через `Edit` с заведомо несуществующей строкой нельзя:
харнесс отклонит такой Edit ещё до хука, и будет ложное «не сработало».)

Пост-проверку проверяют иначе: запиши файл `probe.json` с заведомо битым содержимым
(например `{"a": 1,,}`) — должно прийти сообщение о невалидном JSON. Запись при этом
произойдёт: `PostToolUse` не отменяет действие, он о нём сообщает.
